On 2026-10-08 the user asked to finish migrating `/www/_debian_12` to `/www/_debian_13` on VM-0-2-debian (the OS itself is already Debian 13 trixie; only the per-OS tool-install directory never followed - see [[project_disk_full_git_sync_failure_2026_10_08]] for how this was first discovered via `readlink` on `/usr/local/bin`). Investigated exhaustively before writing any code (systemd units, `/etc/environment` + its backups, `/etc/postgresql/15/main/postgresql.conf`, every `/usr/local/bin` symlink) because the first assumption ("12 is just old, delete it") was wrong, and a second, narrower assumption would have been wrong too.

**The real state is a SPLIT, not a clean old/new boundary** - verified via `readlink -f` on every `/usr/local/bin/*` symlink:
- Still on `_debian_12`: `node`/`npm`/`npx`/`pnpm`/`pnpx`/`yarn`/`yarnpkg`/`corepack` (the real node v26.9.0 binary install), `certbot` (SSL renewal), `pipx`, `poetry`, `uv`, `omp`, `python3.12`, `pi`/`rebrowser-puppeteer` (node-v24.11.1/pnpm-global).
- Already on `_debian_13`: `go`/`gofmt`, `bun`, `pip`/`pip3`, and every pnpm-global CLI (`pm2`*, `tsc`, `ts-node`*, `nodemon`, `serve`, `puppeteer`, `node-gyp`, `ncu`, `js-yaml`, `http-server`) - because `_debian_13/node/v26.9.0/` only ever held `pnpm-global` + `etc` (NOT a real node install), confirmed by `/etc/environment`'s own `NODE_HOME`/`PNPM_HOME`/`BUN_INSTALL` already declaring `_debian_13` as home. **No collision risk merging node's real bin/lib into `_debian_13/node/v26.9.0/`.**
- **Genuine collision, must NOT merge:** `python3_venv` exists on BOTH sides as two unrelated venvs - `_debian_12/python3_venv` (Python 3.12, `home=/usr/bin`, backs the `python3.12` symlink) vs `_debian_13/python3_venv` (Python 3.13, `--system-site-packages`, backs `pip`/`pip3` AND is literally the interpreter for the live `ncore-rustdesk-dashboard.service`, `ExecStart=python3 ...` resolving via `/usr/local/bin/python3`). The migration renames the _debian_12 one to `_debian_13/python3.12_venv` instead of merging.
- **Live services with a raw absolute `WorkingDirectory=`, no symlink indirection:** `rustdesk-hbbr.service` + `rustdesk-hbbs.service` both set `WorkingDirectory=/www/_debian_12/applications/rustdesk-server/data` (holds the ed25519 identity key + sqlite client DB - genuinely stateful, not reinstallable). `postgresql@15-main.service` cluster: `/etc/postgresql/15/main/postgresql.conf` sets `data_directory`/`log_directory` to `_debian_12/postgresql/{data,logs}` (4.9G, live, `pg_lsclusters` confirmed `15 main ... online`; a dead `17 main` cluster exists separately at `/www/wwwroot/postgresql`, unrelated, left alone).
- `/etc/environment` (the live file, not its many `.backup.*` snapshots) has `PIPX_HOME` and `UV_PROJECT_ENVIRONMENT` hardcoded to `_debian_12` paths - must be updated via the existing `set_env_and_var()` helper in `global_var_store.sh` (reused, not reinvented).

**Fix shipped:** `scripts/shells/linux/common/debian_tooldir_migration.sh` - a new idempotent engine, one function per subsystem (node core, node secondary/pi, python system venv, pipx+certbot, poetry, uv, omp, rustdesk-server, postgresql), each stop→move/rsync→verify(smoke test: `--version`/`pg_isready`/`systemctl is-active`)→relink/reconfig→restart, never force-deletes the old copy (renamed aside as `.pre_migration_<timestamp>` only after verification passes; on ANY failure the service is left/reverted to whichever path last verified healthy). `--report-only` mode just lists detected legacy dirs read-only. Auto-detects old/new names generically from `/etc/os-release` (`_<id>_<major>` pattern) so it also covers the *next* hop (13→14), not just this one.

**Wired into dd.sh as ONE merged menu item, not two** (per explicit follow-up from the user: fold it into the same "Upgrade OS -> latest" slot, keep showing it even when the OS itself is already at the latest major/version, and never show Debian-specific wording on Ubuntu or vice versa):
- `scripts/shells/linux/dd_helper/linux_management.sh`: `tooldir_migration_pending()`/`tooldir_migration_label()` stayed as helpers (names derived live from `/etc/os-release` via `tdm_detect_old_dirs`/`tdm_current_name`, so the label is naturally `_ubuntu_<old> -> _ubuntu_<new>` on an Ubuntu host - never hardcoded "Debian" text). `os_upgrade_target_available()` now ALSO returns true when the OS is already at latest but `tooldir_migration_pending` is true; `os_upgrade_target_label()` falls back to `"already <ver>, idempotent tool-dir cleanup: <label>"` in that case. No second menu item/function - `run_os_upgrade()` is the single entry point for both a real hop and the standalone catch-up; the submenu's `upgrade_idx` conditional item covers both. Verified end-to-end on this host: label renders `already 13, idempotent tool-dir cleanup: _debian_12 -> _debian_13`.
- `scripts/shells/linux/debian/install_shells/upgrade_os_to_latest.sh`: `main()`'s "already at latest" early-return branch now also calls `run_post_upgrade_tooldir_migration()` (idempotent no-op if nothing pending) before returning, instead of just printing "already at latest" and exiting - this is what makes the standalone catch-up reachable from the SAME code path a real hop uses. The post-hop call after `cleanup_os_upgrade_artifacts()` is unchanged (covers a *future* major-version hop automatically too). Non-fatal to the upgrade/check itself if it reports issues.

**2026-10-08 first real run surfaced 4 bugs in the script + 1 unrelated live regression - all fixed, details matter if this script misbehaves again:**
1. **`readlink -f` on the node/pnpm symlinks returned empty** once `rsync -a --remove-source-files` + the empty-dir `rmdir` had already removed the old `node/<ver>/bin/` directory - `readlink -f` requires all but the last path component to exist, so it silently failed and the 8 node/npm/pnpm/yarn/corepack symlinks were NEVER repointed, leaving them dangling at the just-deleted old path (**node/npm/pnpm/etc. broken system-wide** until manually fixed). Fix: use raw `readlink` (no `-f`) - it only needs to read the symlink's stored text, not resolve it.
2. **`$USE_SUDO -u postgres pg_isready -q`**: when already root, `USE_SUDO=""`, so this literally executed `-u postgres pg_isready -q` as a command -> `-u: command not found` (exit 127) -> the verification `&&` chain failed -> the script wrongly concluded "did not come up healthy" and reverted postgresql.conf back to the old path, even though PostgreSQL had actually started fine on the new path. No data was lost (the revert is itself safe-by-design), but the migration never completed. Fix: new `tdm_as_postgres()` helper using `runuser -u postgres --` when EUID=0, `sudo -u postgres` otherwise - `-u` always needs a real su/sudo, never `$USE_SUDO` alone.
3. **`tdm_log` wrote to stdout**, and several callers capture a helper's RETURN VALUE via `moved="$(tdm_move_simple ...)"` - any `tdm_log` call inside that helper leaked straight into the captured variable, corrupting it (visible in the original run's garbled uv_bin line: the WARN text got concatenated into the path used for the next `tdm_relink` call and the final "OK" message). Fix: `tdm_log` now writes to stderr unconditionally (still visible on an interactive terminal; never captured by `$(...)`).
4. **False-positive "OK: migrated" on a destination collision**: `tdm_migrate_{python_system_venv,pipx,poetry,uv,omp}` all did `moved="$(tdm_move_simple ...)"; [ -n "$moved" ] || moved="$dst"` - on a genuine collision (destination exists with unrelated content, move correctly refused) this fallback assumed `$dst` anyway and went on to report success, even though nothing had actually moved and the symlink was correctly left untouched by `tdm_relink`'s own guard (this is exactly what happened to `uv`: reported "OK: uv migrated" while `/usr/local/bin/uv` was still pointing at the old, never-moved path). Fix: every caller now checks `moved` for emptiness and calls `tdm_fail` + `return 1` instead of guessing. Also hardened `tdm_move_simple` itself to `rmdir` an empty placeholder directory on the destination side before deciding it's a real collision (this was uv's actual situation: `_debian_13/uv_bin` pre-existed as an empty leftover dir).
5. **Unrelated live regression, NOT caused by this script**: `certbot --version` failed with "cannot execute: required file not found" because `/usr/bin/python3.12` no longer exists - traced via `/var/log/dpkg.log` to `2026-10-08 15:45:3x`, which is the exact timestamp of an `apt-get autoremove -y` run earlier in the SAME session (during Chrome/Edge cleanup, see [[project_disk_full_git_sync_failure_2026_10_08]]) - removing Chrome apparently orphaned `python3.12`/`python3.12-venv`/`python3.12-dev` as no-longer-needed auto-installed deps, and autoremove purged them. certbot's pipx venv had hardcoded `executable = /usr/bin/python3.12` from when it was created. Fixed live with `PIPX_HOME=/www/_debian_13/pipx_home PIPX_BIN_DIR=/usr/local/bin pipx reinstall-all` (rebuilt certbot + its 5 DNS plugins against python3.13, the now-current system python) - **lesson: `apt-get autoremove` after purging a browser is not as safe as it looks; it can silently orphan an unrelated language runtime that other venvs hardcoded a path to.**

**Separately found, NOT caused by this migration, NOT fixed (flagged only):** `poetry --version` fails with `ModuleNotFoundError: No module named 'poetry'` even after a clean move+relink+sed-fix, because `poetry_venv/bin/python3` is a *relative* symlink chain (`-> python -> /usr/local/bin/python`) that ends up `exec`ing into the unrelated `_debian_13/python3_venv` (the rustdesk_dashboard/pip venv) via a pre-existing wrapper at `/usr/local/bin/python` (`exec "/www/_debian_13/python3_venv/bin/python3" "$@"`, dated Sep 18, predates this task). Poetry's own site-packages are real and present at the new location but never consulted, because the executed interpreter's `pyvenv.cfg` lookup resolves to the OTHER venv. This cross-wiring already existed identically on the `_debian_12` side before migration (same relative-symlink target, same wrapper) - not a regression, just surfaced by the smoke test. Left alone pending the user's call (don't understand original intent of that wrapper; out of scope to restructure without asking).

**2026-10-08 second round - user required every bug be self-healed IN THE SCRIPT'S OWN FLOW, not patched by hand. Iterated to a genuinely clean run (9 done, 2 skipped, 0 failed, then settled at 7/2/2 once an unsafe self-heal was removed - see below). Key lessons from building the self-healing:**

- **`tdm_repair_foreign_venv_interpreter` (new, generic):** a venv's `bin/python3` can resolve into a totally DIFFERENT venv through an external wrapper (this host has `/usr/local/bin/python`/`python3`/`python3.12`/`python3.13` ALL as 127-byte shell scripts that `exec` into `_debian_13/python3_venv` - confirmed every single one is wrapped, none are real). **Static `readlink -f` cannot detect this** (it only follows symlinks, not a script's own `exec`). The only reliable detection is asking the interpreter at runtime: `"$py_bin" -c 'import sys; print(sys.prefix)'` and comparing to the venv's own real path. Fixed poetry this way (it was running AS `_debian_13/python3_venv`, so its own installed package was never on sys.path despite being physically present).
- **The repair target must bypass `/usr/local/bin/python*` entirely** (all wrapped on this host) - go straight to `/usr/bin/python3` (verified: a real symlink to a real binary, not a script), and verify the candidate itself reports `sys.prefix=/usr` before trusting it (belt-and-suspenders against yet another layer of wrapping).
- **Unconditional repair is NOT safe - test first, repair only if broken.** Applying the above repair to `pipx_venv` ITSELF broke `pipx` system-wide: `pipx_venv`'s own pip-installed copy is version-locked to python3.12 (gone), so it only ever worked by *accident* - its wrapper-hijacked chain into `_debian_13/python3_venv` (which has `include-system-site-packages=true`) reached the real apt-installed `pipx` module at `/usr/lib/python3/dist-packages/pipx` (apt package `pipx 1.7.1-1`, arch `all`). "Fixing" the isolation removed that escape hatch. **Rule now baked into every migrate_* function: call `tdm_repair_foreign_venv_interpreter` only after a smoke test has already failed, never preemptively.**
- **Better fix for pipx specifically: prefer the apt-maintained `/usr/bin/pipx` launcher outright** over pipx_venv's fragile private copy - it's always correct, matches whatever `pipx` apt package is installed, needs no repair, and is what the rest of the script (certbot/poetry's pipx fallback) already assumes is on PATH.
- **`tdm_pipx_heal_if_broken` (new):** after any pipx-related move, `pipx list` is checked for "invalid interpreter"/"missing python interpreter" and `pipx reinstall-all` is run automatically if so - this is what actually fixes the certbot/python3.12-removed-by-autoremove class of failure (rebuilds every pipx app fresh against whatever python pipx itself currently resolves to).
- **A venv whose packages are pinned under `lib/python3.12/site-packages` cannot be fixed by symlink repair alone when python3.12 doesn't exist anywhere** (same root cause as certbot) - the only real fix is a fresh reinstall. `tdm_migrate_poetry` now falls back to `PIPX_HOME=... PIPX_BIN_DIR=/usr/local/bin pipx install poetry --force` when the relink+repair combo still leaves `poetry --version` broken - this is now how poetry is migrated on this host (its dedicated `poetry_venv` is bypassed in favor of a pipx-managed install).
- **False-positive idempotency on leftover residue:** `pipx_home`'s move kept reporting a hard collision on every re-run because cache/log files pipx itself writes (`.cache`, `py/CACHEDIR.TAG`, `logs/cmd_*.log`) were left behind at the old path after the real content had already moved. Fixed: if the destination already has `venvs/` (proof of a prior real migration), the leftover source residue is swept and treated as already-done, instead of failing forever.
- **Self-healing must never GUESS a package name.** Added, then had to partially REVERT, a fallback that ran `pnpm add -g "$link"` when a pnpm-global tool's relink target had vanished (this happened to `pi`/`rebrowser-puppeteer` - their whole `node-v24.11.1/pnpm-global` tree was lost, cause still unconfirmed, likely from the first buggy run before the `readlink -f`/rsync fixes above). `rebrowser-puppeteer` is an exact, unambiguous real package name and the guess happened to be right. **`pi` is NOT** - `pnpm add -g pi` silently installed an unrelated real npm package (a decimal-places calculator) that shares the name, which is *worse* than reporting it missing (a confidently-wrong tool instead of an honestly-broken one). Removed the auto-reinstall entirely; the script now only ever reports "relink target missing - reinstall manually, verify the name first" for this class of failure. **Lesson: an automated fix that silently installs the wrong thing under a correct-looking name is strictly worse than a clear failure message - never add a remediation step whose correctness depends on guessing a name.**
- Also manually un-wound the bad guess on this host (`pnpm remove -g pi`) and fixed `rebrowser-puppeteer`'s install so it works via its own pnpm-managed PATH entry (`/www/_debian_13/node/v26.9.0/pnpm-global/bin/rebrowser-puppeteer`, already on PATH via `/etc/profile.d/pnpm-global-bin.sh`) rather than via a direct `/usr/local/bin` symlink - **pnpm's own bin shims assume they are reached through pnpm's own path, not an externally-added symlink; direct-symlinking one from elsewhere breaks its internal relative module resolution.** Left `pi` genuinely unreinstalled - its correct package identity is unknown.

**Final verified-clean state after this round:** node/npm/pnpm/yarn/corepack, python3.12, pipx, certbot, poetry, uv, omp, PostgreSQL (15 databases, live-verified via `psql`), rustdesk-hbbr/hbbs (both active) - all confirmed working via direct smoke test, not just the script's own report. Two honest remaining failures, left exactly as reported (not papered over): `pi` (unknown correct package, needs a human who remembers what it was), and a cosmetic stale `/usr/local/bin/rebrowser-puppeteer` symlink (the tool itself works fine via PATH regardless).

**How to apply:** Never assume `/www/_debian_<N>` for any N is safely deletable on this host without re-running the `readlink`/systemd-unit/`/etc/environment` audit above - the live/legacy boundary does not follow a clean "N = old" rule, it's per-subsystem and was already drifting before this fix. If the migration script ever needs a third round (e.g. 13→14 later), it is already generic - just run it again via the same dd.sh menu item or let the OS-upgrade hook fire it automatically. Not yet run on this host as of this writing - the user asked to review/run it themselves; code is committed via the server's own `code_sync` scheduler cycle (verified: that scheduler auto-commits+pushes uncommitted local changes on its own cadence, e.g. commit `c7cc1861c` picked up the unrelated browser-install fix from the same session without being asked).
