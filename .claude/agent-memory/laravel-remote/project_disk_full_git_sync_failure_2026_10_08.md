On 2026-10-08, `/` on VM-0-2-debian hit 99% full (59G used, 687M free), which broke `git pull`/`git push` in `/www/programing/core_node`: fetch received objects from GitHub but failed `unable to write loose object file: No space left on device` → `unpack-objects failed` → pull aborted → subsequent push rejected as non-fast-forward ("fetch first"), even though the real cause was disk space, not a real divergence.

**Why:** This repo auto-syncs very frequently (gitsync pushes commits every ~5min from multiple machines, see recent commit log pattern `*-pycore-auto-gitsync`), so a full disk here will recur and silently break every machine's sync until someone frees space. `/var`, `/boot`, and PG data are NOT the big consumers on this host — `/www` (33G, incl. `/www/wwwroot/laravel_db` 15G and `/www/programing` 11G) and `/root` (8.5G, almost entirely regenerable tool caches) are.

**Safe cleanup recipe (all regenerable caches, verified safe — none touch running services or [[project_relay]] data):**
- `rm -rf /root/.npm/_cacache` (~465M) — npm redownloads on demand
- `rm -rf /root/.cache/{pnpm,composer,node-gyp,code-server,electron,go-build,node}/*` (~800M combined) — all rebuild/redownload lazily
- `apt-get autoremove -y && apt-get clean` — drops stale kernel headers (e.g. old `linux-headers-6.1.0-37-*` when running 6.12.x) and unused libs
- `journalctl --vacuum-time=2d` — usually frees ~0 here since journal is small (140M), not worth prioritizing
- Freed ~2.5G total (99%→95% used, 687M→3.1G free) in this incident without touching anything live.

**Round 2 (same incident, user asked to find more — excluding laravel DB and audio data explicitly):** freed another ~6.6G (95%→84% used, 3.1G→9.7G free):
- `rm -rf /var/_core_node/cache/pip/http-v2` (2.6G) — this project's own pip HTTP cache dir (separate from `~/.cache/pip`; check `pip config list` / `PIP_CACHE_DIR` env — the project routes pip cache under `/var/_core_node/cache/pip`), safe, pip redownloads wheels on demand.
- Cargo re-downloadable parts only, toolchain kept (matches the repo's own policy in `scripts/shells/linux/dd_helper/dev_cache_cleanup.sh`): `rm -rf /root/.cargo/registry/{cache,src}/* /root/.cargo/git/checkouts /root/.rustup/downloads` (~250M). **Do not remove `/root/.rustup/toolchains` itself** — that script explicitly keeps installed toolchains, only cleans downloads/registry cache/src/checkouts.
- `/root/.codex/packages/standalone`, `.tmp/plugins`, `plugins/cache`, `cache/remote_plugin_catalog` (~570M) — Codex CLI's own redownloadable package/plugin caches.
- `/root/.local/share/cursor-agent/versions/*` — cursor-agent self-update keeps every old version; safe to delete all but the newest (check `readlink -f $(command -v cursor-agent)` or the newest-dated dir) (~783M freed, one dir kept).
- `/root/.local/share/gem/ruby/*/doc/*` (239M) — Ruby gem documentation (ri/rdoc), gems still work without it; keep `gems/`, `extensions/`, `cache/` siblings.
- pnpm global store, two locations: `/root/.local/share/pnpm` and `/var/_core_node/cache/xdg/pnpm` (~1.5G combined) — safe, pnpm repopulates content-addressable store from registry on next install.
- Headless Chrome cache `/var/_core_node/cache/xdg/google-chrome-headless` (103M) — only safe if confirmed not running (`ps aux | grep chrome`); it was idle in this incident.
- `git gc --aggressive --prune=now` on `/www/programing/core_node/.git` shrank it from 2.4G → 1.1G (~1.3G freed). Verified safe afterward with `git fsck --full` (clean) and `git status` (clean, in sync with origin). Safe to re-run anytime the repo's `.git` looks bloated — this repo churns a lot of history via frequent auto-sync commits.

**Confirmed LIVE / do-not-touch (verified via `ps aux` / mount, not just guessed):** `/www/_debian_12/postgresql/data` — actual Postgres `-D` data dir, a live `postgres` process uses it (this is the laravel DB — always excluded per user instruction). `/www/_debian_13/python3_venv` — has a live process (`rustdesk_dashboard/app.py`) running out of it. All `*audio*` dirs live under `/www/wwwroot/laravel_db/` (`worker_audio`, `agent_history_audio`, `tts_data/audio`, `static/app_qy_v1/audio`) — always excluded per user instruction (audio data).

**Still NOT touched (identified but deferred — ambiguous risk/ownership, flagged to user instead of deleting):** `/www/wwwroot/.tmp` (294M, owned by `lighthouse` user, looks like aapanel/BT panel installer temp dirs from Sep–Dec 2025, outside core_node scope); `/root/.rustup/toolchains` itself (1.4G, kept per project policy above); `/www/_debian_12` and `/www/_debian_13` non-postgres/venv subdirs (bun/go/node/pipx/omp, several hundred MB each) — these are the panel's per-OS sandboxed runtime installs, not caches, left alone since ownership/usage outside core_node wasn't fully verified; `/root/.codex/sessions` (364M AI session history logs) — not a cache, deferred rather than deleted.

**How to apply:** If a future git push/pull on this server fails with "No space left on device" or an unexplained non-fast-forward rejection, check `df -h /` first — it is very likely disk space, not a real conflict. Run both rounds of the cache-cleanup recipe above before troubleshooting git itself, then `git gc --aggressive --prune=now` on `.git` if it's grown large. Always verify a path is not live (`ps aux`, `mount`) before deleting anything outside `~/.cache`-style dirs, and always exclude `/www/wwwroot/laravel_db` (DB + audio data) unless the user says otherwise.

**Round 3 — CRITICAL CORRECTION: `/www/_debian_12` is NOT legacy/stale, it is the live system toolchain root.** The user asked to "finish migrating debian 12 to 13 and delete the old dir," assuming the OS-level upgrade (host is now Debian 13 trixie) meant the tool directories migrated too. It did not. Verified via `readlink` on every symlink in `/usr/local/bin`: **16 live symlinks point directly into `/www/_debian_12/`** — `node`/`npm`/`npx`/`pnpm`/`pnpx`/`yarn`/`yarnpkg`/`corepack` (node v26.9.0), `python3.12`, `pipx`, `poetry`, `uv`, `omp`, `certbot` (SSL renewal!), `pi`/`rebrowser-puppeteer` (pnpm-global). Deleting `_debian_12` would break Node/npm/Python/pip-tooling/SSL-cert-renewal system-wide. Its `postgresql/data` (4.9G, [[project_relay]] DB) is separately confirmed live via `ps aux`. `/www/_debian_13` (950M) is a **second, partially-populated, parallel** toolchain dir (newer script runs compute `_debian_13` since OS is now 13) — also partly live (a `python3_venv` process for `rustdesk_dashboard`). Neither is safe to delete.

This divergence is a known, already-tracked architecture debt, documented in `.claude/agents_shared/d30/audit_result.json` and `development-guides/DIRECTORY_NAMESPACE_RULES.md` section 2: these `_debian_12`/`_debian_13` top-level dirs under `/www` are explicitly called "legacy," the canonical target is `/opt/core_node/_<os>_<ver>` (via `service_contract.json#paths.drive_layout.namespaces`), and multiple scripts (`gvar_common.sh` `get_dev_compile_base`, `pyfoundations/system_paths.py` `_get_dev_compile_base`, `nodetools/gvar_common.js`) still produce the old `/www/_debian_<ver>` or `/opt/_debian_<ver>` paths instead of the contract path — **flagged as bugs, not yet fixed**. The doc is explicit: "Moving them into a namespace is a migration step that needs the user's explicit approval... Scripts keep reading them until the migration is done." `/opt/core_node/_debian_13` (the correct target) already exists but is nearly empty (12K) — migration hasn't started.

**How to apply (corrected):** Never delete or "clean up" `/www/_debian_12` or `/www/_debian_13` as a quick disk-space action. If asked to migrate/consolidate them, this is a real engineering task (fix the path-resolution functions listed above to read the contract, re-point all 16+ `/usr/local/bin` symlinks, relocate the live Postgres data dir with a proper stop/rsync/repoint-`PGDATA`/start/verify sequence, then only delete the old dirs once every consumer is confirmed repointed) — scope it as a project task, not a casual cleanup, and always re-verify current symlink targets with `readlink` before assuming anything is stale, since OS-version-named dirs here do NOT reliably track the actual running OS version.

**Round 4 — Chrome/Edge were the ONE real "always installs regardless of mode" bug; fixed at the source.** User asked to uninstall Chrome+Edge and make server installs skip browsers + other unnecessary apps by default. Audited every optional-app install flag across `scripts/shells/linux/debian/install_shells/*.sh` against `selector_common.sh`'s `MENU_CONFIG` (the mode-preset table for `base/server/full/desktop`). Finding: Flutter (`59_install_flutter.sh`), Android Studio (`61_install_android_studio.sh`), and LibreOffice (inside `63_install_ittools_binaries.sh`) **already** skip correctly on headless hosts via `[ "$HAS_DESKTOP_ENVIRONMENT" = false ]` guards (force with `INSTALL_FLUTTER=true` / explicit android flag / `INSTALL_LIBREOFFICE=true`) — these are fine, not bugs. Samba defaults to a safe no-op when unset. **Only `41_install_browsers.sh` lacked this guard** — `chrome_ensure()`/`edge_ensure()` only checked `INSTALL_CHROME`/`INSTALL_EDGE` against the literal string `"false"`, and since neither var has a `MENU_CONFIG` row, `get_var` returns empty/unset, which is `!= "false"` → browsers installed unconditionally on every mode including `server`/`base`.

Fix applied (matches the exact sibling idiom, not a new mechanism): added to both `chrome_ensure()` and `edge_ensure()` in `scripts/shells/linux/debian/install_shells/41_install_browsers.sh`, right after the existing `INSTALL_<X>=false` removal check:
```bash
if [ "${HAS_DESKTOP_ENVIRONMENT:-false}" = "false" ] && [ "$INSTALL_CHROME" != "true" ]; then
    browser_log "No desktop environment detected: skipping Google Chrome install (~432M). Set INSTALL_CHROME=true to force."
    return 0
fi
```
(same for Edge). `HAS_DESKTOP_ENVIRONMENT` is already in scope (set by `runtime_environment.sh`, sourced transitively via `gvar_common.sh`; the same file already used it for `chrome_ensure_shortcut`, just never for the actual package install). Verified `bash -n` syntax-clean. Did NOT touch `selector_common.sh`'s `MENU_CONFIG` table — the headless-environment check is a better, lower-risk fix than adding menu rows (no TUI state-sync risk, and it correctly also covers a `desktop`-labeled mode that happens to run headless).

**Follow-up lesson (discovered 2026-10-08, same day, via [[project_debian_12_to_13_tooldir_migration]]):** the `apt-get autoremove -y` run after purging Chrome/Edge below silently orphaned-and-removed `python3.12`/`python3.12-venv`/`python3.12-dev` (confirmed via `/var/log/dpkg.log` timestamp match) because they'd been pulled in as Chrome's auto-installed deps at some point. This broke `certbot`'s pipx venv (hardcoded `/usr/bin/python3.12` interpreter) hours later, surfaced only when something else tried to use it. **Lesson: after `apt-get purge` on anything, treat the follow-up `apt-get autoremove` as needing a real diff review (`apt-get autoremove --dry-run` first), not just a blind yes - a removed "auto-installed" package can be a language runtime something unrelated depends on by hardcoded absolute path.**

Manually uninstalled both from this server right after (user confirmed-is-live DB/audio excluded, browsers were not excluded): `apt-get purge -y google-chrome-stable microsoft-edge-stable`, removed `/etc/apt/sources.list.d/google-chrome.list` + its gpg key, `/usr/local/bin/{google-chrome,microsoft-edge,google-chrome-rlimit,microsoft-edge-rlimit}` symlinks/wrappers, `/etc/opt/{chrome,edge}/policies/managed/corenode_memory.json`, `/opt/google` + `/opt/microsoft`, then `apt-get autoremove -y` (dropped now-orphaned GTK libs). Freed ~1.1G. No running process or systemd unit depended on either browser at removal time (checked first).

**FrankenPHP `src/` IS safe to delete (done, freed 4.1G):** `/www/programing/frankenphp` is itself defined as `FRANKENPHP_STATIC_WORK_ROOT="${CN_CACHE_ROOT}/frankenphp"` in `scripts/shells/linux/common/frankenphp_static_builder.sh` — i.e. a **cache root** by the project's own naming, not persistent source. `src/` (`FRANKENPHP_STATIC_SRC_DIR`) is a git checkout that `fm_static_git_ensure()` re-clones/re-checks-out automatically on the next build if missing (pinned to the version tag matching the currently-running binary). The live FrankenPHP service runs from the separately-installed `/usr/bin/frankenphp` binary and never touches `src/`. Removed `rm -rf /www/programing/frankenphp/src` (4.5G → 349M for the whole frankenphp dir); verified the running `frankenphp` process (serving laravel_main via Caddyfile) was unaffected. Keep `prebuilt/`, `prebuilt-staging/`, `acme.sh/`, `certs/`, `runtime/` — only `src/` was the disposable build-scratch tree.
