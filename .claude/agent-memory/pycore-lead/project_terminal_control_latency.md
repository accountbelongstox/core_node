Terminal Control page was slow / empty because of several stacked causes:

- Relay API `api.si.12gm.com` (server corenode-ssh1, 2 CPU, 4-thread FrankenPHP pool) hung: pool exhausted by `/api/queue-center/overview` + dictionary lane rebuild (`select *` on a 240k-row table, `cursor()` ignores column args) and unit CPUQuota=25% (=25% of ONE core). laravel-remote fixed it (DictLane*.php, CPUQuota runtime 100%, 175_laravel_main_start.sh default). Symptom: TLS ok, `/up` and `/api/*` time out while `/favicon.ico` and mercure answer.
- pycore process saturated (~1.2-1.5 cores of Python) so EVERY serialized hop / ctypes call / sqlite row fetch pays a GIL switch interval (5 ms+). A row-per-key `fetchall()` of 1787 rows took 6-17 s; 170 ctypes window calls took 1.2 s. Rule: on hot request paths use ONE aggregate row (`json_group_object`) and few THREAD_BUS hops; never per-row/per-call loops.
- Biggest single burner found: `_UserDataDocument` (user_data_store.py) rewrote 2.4 MB `user_data.json` (task_history) and 7.7 MB `queue_center_segments.json` every 2-5 s with 3 deep copies + pure-Python `json.dump(indent=2)` + fsync (0.65 -> 0.065 s per write after fix). Still open: the cadence itself (task_history and diff segments should not live in a rewrite-whole-file document); AudioQueuePersist rewrites a 13.7 MB snapshot (leftover 40 MB `.tmp` files in cache/audio_queue from interrupted writes).
- Snapshot was computed on each `ui/terminal/windows` request; now `TerminalSnapshotCollector` (pyctl/terminal) collects on a background thread while a viewer lease is live, requests read the stored snapshot, changes are pushed as `terminal.changed` with `snapshot` (logs omitted, <=48 KB) through the relay device event; the UI applies pushed snapshots (`commitPushedSnapshot` in PcTerminalPage.tsx) and only falls back to a `windows` op when a log count changed.
- `ThreadBus` state operations ran on ONE `ThreadBusStateThread` (queue + Event per operation); a single serialized call cost 0.55 s with one CPU-bound thread in the process (0.6 ms idle). Now `ThreadBusStateOwner` runs them inline under one RLock (0.063 s in the same test, stress-tested: queues, signals, serialized owners, events). Every `call_serialized` hop is ~10 bus operations, so hop count still matters; the terminal request path is now ONE hop (`read`), lease renewal every 5 s, decoration done by the collector via `register_snapshot_decorator`.
- Open: a burst of ~20 parallel requests to trivial routes still takes 5-25 s in a busy pycore (page load fires ~40); background CPU is diffuse (audio queue export/persist, CodeSync-Stats, agent-history scans, AudioResourceLedger); measured top thread CPU per 10 s: 1-2.6 s each of ~12 s total.
- Dev hot-reload (`dev_reload.py`, on by default) execs a new interpreter on any pycore .py change; a syntax error left NO backend running (nothing supervises the exec). Now changed files are compiled first and the restart is held while any fails. Other agents' edits restart pycore every 1-3 min, and each boot burns ~70 CPU-s; measure only >3 min after a restart.

**Why:** user asked why the pycore UI is slow; findings above with numbers in the task report.
**How to apply:** when a pycore route is slow, first sample threads (sys._current_frames + psutil per-thread CPU deltas from a temporary daemon thread appended to a module; remove it after) instead of guessing; wall time >> isolated time means GIL/queue contention, not the algorithm. Temporary instrumentation via Bash heredocs loses backslashes: write edit scripts with the Write tool and use `chr(92)`; a broken temp edit kills pycore (hot reload exec), keep a copy of the original in the scratchpad.
