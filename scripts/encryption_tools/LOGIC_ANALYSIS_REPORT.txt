1.1 入口条件检查 (第 90-92 行)

检查项：加密目录是否存在

代码逻辑：
  if [ ! -d "$encrypted_dir" ] && [ ! -d "$batch_encrypted_dir" ]; then

  fi

触发条件：

  ✓ 如果至少有一个目录存在
    → 继续执行解密检查流程

结论：只有在存在加密文件时才会继续检查

操作：

1.3 个别加密文件检查 (第 110-118 行)
────────────────────────────────────────────────────────────────────────
检查项：already_encrypted/ 中的每个 .js 文件

代码逻辑：
  while IFS= read -r -d '' enc_file; do
      base_name="$(basename "$enc_file")"
      base_name="${base_name%.js}"
      raw_file="$raw_dir/$base_name"
      if [ ! -s "$raw_file" ]; then
          pending_files+=("$enc_file")
      fi
  done

逐文件检查：
  对 already_encrypted/ 中的每个 .js 文件：
    1. 提取文件名（去掉 .js 后缀）
    2. 检查 .secret_ignore/$文件名 是否存在且不为空
    3. 如果不存在或为空 → 加入 pending_files[] 数组

关键特性：
  ✗ 不检查文件修改时间
  ✗ 不检查加密文件是否更新
  ✓ 只检查解密文件是否存在且不为空
  
结论：即使加密文件更新了，只要 .secret_ignore/ 中有文件就不会重新解密


1.4 批量加密包检查 (第 101-108, 124-149 行)
────────────────────────────────────────────────────────────────────────
检查项：already_batch_encrypted/ 中的批量包

阶段1：检测批量包是否存在 (第 101-108 行)
  if [ -d "$batch_encrypted_dir" ]; then
      bundle_count=$(find "$batch_encrypted_dir" -type f -name '*.js' | wc -l)
      if [ "$bundle_count" -gt 0 ]; then
          has_batch_bundle=true
          bundle_file=$(第一个 .js 文件路径)
      fi
  fi

阶段2：检查批量包是否需要解密 (第 124-149 行)
  if [ "$has_batch_bundle" = true ]; then
      # 读取批量包中的文件总数 (TOTAL_COUNT)
      bundle_file_count=$(从批量包 JS 代码中提取 TOTAL_COUNT)
      
      # 统计 .secret_ignore/ 中现有文件数量
      raw_file_count=$(find "$raw_dir" -type f | wc -l)
      
      # 判断是否需要解密
      if [ "$bundle_file_count" -gt 0 ] && 
         [ "$raw_file_count" -lt "$bundle_file_count" ]; then
          bundle_needs_decrypt=true
      fi
  fi

触发解密条件：
  ✓ 批量包中的文件数 > .secret_ignore/ 中的文件数
  ✓ 说明有文件还未解密

关键特性：
  ✗ 不检查批量包文件修改时间
  ✗ 不对比个别文件名
  ✓ 只对比文件总数

结论：只要 .secret_ignore/ 中的文件数 < 批量包文件数，就触发解密


1.5 决定是否需要解密 (第 120-122, 151-153 行)
────────────────────────────────────────────────────────────────────────
最终判断：

检查点1 (第 120-122 行)：
  if [ ${#pending_files[@]} -eq 0 ] && [ "$has_batch_bundle" = false ]; then
      return 0
  fi

  条件：pending_files 为空 且 没有批量包
  结果：直接返回，不需要解密

检查点2 (第 151-153 行)：
  if [ ${#pending_files[@]} -eq 0 ] && [ "$bundle_needs_decrypt" = false ]; then
      return 0
  fi

  条件：pending_files 为空 且 批量包不需要解密
  结果：直接返回，不需要解密

触发解密的条件：
  ✓ pending_files[] 中有文件 (个别加密文件缺失)
    或
  ✓ bundle_needs_decrypt = true (批量包文件数 > 解密文件数)


1.6 解密模式选择 (第 155-185 行)
────────────────────────────────────────────────────────────────────────
决策树：

情况A：has_batch_bundle = true 且 pending_files[] > 0
  → 显示选择菜单：
    [1] 批量模式 (Bundle) - 快速
    [2] 个别模式 (Original) - 兼容
  → 等待用户输入
  → 根据选择设置 use_batch_mode

情况B：has_batch_bundle = true 且 pending_files[] = 0
  → 自动选择：use_batch_mode = "yes"

情况C：has_batch_bundle = false
  → 自动选择：use_batch_mode = "no"

结论：
  - 两种模式都可用时 → 让用户选择
  - 只有一种模式时 → 自动使用该模式


1.7 执行解密 (第 268-310 行)
────────────────────────────────────────────────────────────────────────
批量模式 (use_batch_mode = "yes")：

  命令：
    "$node_cmd" "$bundle_file" pwd "$password" "$raw_dir"
  
  特点：
    ✓ 单次 Node.js 进程启动
    ✓ 一次性解密所有文件
    ✓ 速度快 (~0.1秒)

个别模式 (use_batch_mode = "no")：

  命令（循环）：
    for enc_file in "${pending_files[@]}"; do
        "$node_cmd" "$enc_file" pwd "$password" "$raw_dir"
    done
  
  特点：
    ✓ 多次 Node.js 进程启动
    ✓ 逐个解密文件
    ✓ 速度慢 (~2-3秒，48个文件时)

    3. 加密新文件
    4. 追加到数组

2.3.3 替换批量包中的文件
  命令：
    node bundle_add_file.js 批量包.js 文件 密码 --replace
  
  操作：
    1. 读取现有批量包
    2. 查找同名文件
    3. 重新加密
    4. 替换数组中的对应项
    5. 重新生成批量包

2.3.4 删除批量包中的文件
  命令：
    node bundle_remove_file.js 批量包.js 文件名
  
  操作：
    1. 读取现有批量包
    2. 从数组中删除指定文件
    3. 重新生成批量包

2.3.5 查看批量包内容
  命令：
    node bundle_list_files.js 批量包.js
  
  显示：

三、关键决策点分析
================================================================================

3.1 为什么不检查时间戳？
────────────────────────────────────────────────────────────────────────
设计原因：
  1. 安全性考虑
     - 避免频繁解密增加密码泄露风险
     - 用户明确控制何时需要重新解密
  
  2. 性能考虑
     - 避免每次启动都重新解密
     - 解密是耗时操作（特别是个别模式）
  
  3. 用户控制
     - 用户更新密钥后主动删除 .secret_ignore/ 文件
     - 明确表达重新解密的意图

手动触发重新解密的方法：
  方法1：删除所有解密文件
    rm -rf .secret_keys/.secret_ignore/*
  
  方法2：删除特定文件
    rm .secret_keys/.secret_ignore/API_KEY_1
  
  方法3：调用菜单选项
    运行 dd.sh → 选择 "Clear and Re-decrypt"


3.2 批量包如何判断需要解密？
────────────────────────────────────────────────────────────────────────
判断方法：文件数量对比

原理：
  bundle_file_count = 批量包中的 TOTAL_COUNT
  raw_file_count = .secret_ignore/ 中的文件数
  
  if bundle_file_count > raw_file_count:
      需要解密

优点：
  ✓ 简单高效
  ✓ 不需要读取批量包详细内容
  ✓ 避免文件名对比的复杂性

局限：
  ✗ 如果 .secret_ignore/ 中有其他非密钥文件，可能误判
  ✗ 不能判断具体缺少哪个文件

解决方案：
  .secret_ignore/ 目录应该只包含解密后的密钥文件
  （已在 .gitignore 中排除）


3.3 双模式共存的处理策略
────────────────────────────────────────────────────────────────────────
场景分析：

场景1：只有个别加密 (已有系统)
  检测：has_batch_bundle = false, pending_files[] > 0
  策略：自动使用个别模式
  结果：逐个解密缺失的文件

场景2：只有批量包 (新系统)
  检测：has_batch_bundle = true, pending_files[] = 0
  策略：自动使用批量模式
  结果：一次性解密所有文件

场景3：两种都存在
  检测：has_batch_bundle = true, pending_files[] > 0
  策略：提示用户选择
  选项：
    [1] 批量模式 - 使用批量包解密
    [2] 个别模式 - 使用个别文件解密
  结果：按用户选择执行

设计优点：
  ✓ 向后兼容原有系统
  ✓ 逐步迁移到批量模式
  ✓ 用户可以根据情况选择

四、性能对比分析
================================================================================

4.1 解密性能对比 (以 48 个文件为例)
────────────────────────────────────────────────────────────────────────
个别模式：
  进程启动：48 次
  耗时：~2-3 秒
  内存：48 × Node.js 进程开销
  
  时间分解：
    - 每次 Node.js 启动：~50ms
    - 每个文件解密：~10ms
    - 总计：48 × 60ms ≈ 2.88s

批量模式：
  进程启动：1 次
  耗时：~0.1 秒
  内存：1 × Node.js 进程开销
  
  时间分解：
    - Node.js 启动：~50ms
    - 48 个文件解密：48 × 1ms ≈ 48ms
    - 总计：~98ms

性能提升：
  速度：20-30 倍
  内存：48 倍减少
  CPU：显著降低


4.2 加密性能对比
────────────────────────────────────────────────────────────────────────
个别加密：
  需要：48 次命令调用
  脚本复杂度：需要循环

批量加密（一次性创建）：
  需要：1 次命令调用
  便捷性：高

批量加密（增量添加）：
  添加 1 个文件：1 次命令
  操作：读取 + 追加 + 重写
  耗时：略高于创建单个文件，但仍很快

五、安全性分析
================================================================================

5.1 加密强度 (两种模式相同)
────────────────────────────────────────────────────────────────────────
算法：AES-256-GCM
密钥派生：PBKDF2
  - 哈希：SHA-512
  - 迭代：1,000,000 次
  - 双重派生（额外安全层）

完整性验证：HMAC-SHA512
随机性：每个文件独立的 salt, IV, pepper

结论：符合行业标准，安全强度高


5.2 反取证特性
────────────────────────────────────────────────────────────────────────
错误密码处理：
  - 不返回错误
  - 生成虚假随机数据
  - 避免暴力破解判断正确性

设计目的：
  防止攻击者通过错误信息判断密码正确性


5.3 批量包额外考虑
────────────────────────────────────────────────────────────────────────
优点：
  ✓ 单文件管理简单
  ✓ 原子性操作
  ✓ 备份方便

风险点：
  ⚠ 单点故障（文件损坏则全部无法解密）
  
解决方案：
  ✓ 保留个别加密文件作为备份
  ✓ 定期备份批量包
  ✓ 双模式共存提供冗余

6.1 推荐的迁移路径

阶段3：完全切换

  2. 备份个别加密文件
  3. 主要使用批量模式


6.2 日常操作建议
────────────────────────────────────────────────────────────────────────
添加新密钥：
  node bundle_add_file.js bundle.js new_key.txt password
  rm .secret_keys/.secret_ignore/new_key
  bash dd.sh  # 重新解密

更新现有密钥：
  node bundle_add_file.js bundle.js key.txt password --replace
  rm .secret_keys/.secret_ignore/key
  bash dd.sh  # 重新解密

删除密钥：
  node bundle_remove_file.js bundle.js KEY_NAME
  rm .secret_keys/.secret_ignore/KEY_NAME

强制全部重新解密：
  rm -rf .secret_keys/.secret_ignore/*
  bash dd.sh

────────────────────────────────────────────────────────────────────────
必须备份：
  ✓ .secret_keys/already_batch_encrypted/
  ✓ .secret_keys/already_encrypted/ (备用)

不需备份：
  ✗ .secret_keys/.secret_ignore/ (可重新生成)

备份频率：
  - 每次修改密钥后
  - 定期自动备份（建议每天）

七、故障排查
================================================================================

7.1 解密失败
────────────────────────────────────────────────────────────────────────
症状：解密时报错或生成空文件

可能原因：
  1. 密码错误
     → 检查密码是否正确
  
  2. 批量包损坏
     → 检查文件完整性
     → 使用 bundle_list_files.js 查看
     → 恢复备份
  
  3. Node.js 版本问题
     → 确认 Node.js 已安装
     → 版本建议 >= 14.0


7.2 性能问题
────────────────────────────────────────────────────────────────────────
症状：解密很慢

检查：
  1. 是否在使用个别模式？
     → 切换到批量模式
  
  2. 文件数量是否很多？
     → 批量模式可以处理数百个文件


7.3 文件缺失
────────────────────────────────────────────────────────────────────────
症状：某些密钥解密后不存在

检查：
  1. 查看批量包内容
     node bundle_list_files.js bundle.js
  
  2. 检查是否在批量包中
     → 如果不在，需要添加
  
  3. 检查 .secret_ignore/ 权限
     → 确保可写

八、总结
================================================================================

8.1 核心设计原则
────────────────────────────────────────────────────────────────────────
1. 只在文件缺失时触发解密
   ✓ 不检查时间戳
   ✓ 用户主动控制重新解密

2. 双模式共存
   ✓ 向后兼容
   ✓ 平滑迁移
   ✓ 互为备份

3. 性能优先
   ✓ 批量模式 20-30 倍提升
   ✓ 单进程处理

4. 安全可靠
   ✓ AES-256-GCM
   ✓ 1,000,000 次迭代
   ✓ 独立加密参数


8.2 触发解密的明确条件
────────────────────────────────────────────────────────────────────────
个别模式触发条件：
  ∃ file ∈ already_encrypted/ 
    where .secret_ignore/file 不存在

批量模式触发条件：
  count(批量包中的文件) > count(.secret_ignore/中的文件)

绝不触发条件：
  ✗ 加密文件被修改
  ✗ 加密文件比解密文件新
  ✗ 加密文件时间戳变化


8.3 加密操作要点
────────────────────────────────────────────────────────────────────────
✓ 加密是手动操作
✓ 使用专用工具
✓ 支持增删改查
✓ 操作后需手动触发重新解密（删除 .secret_ignore/ 文件）
