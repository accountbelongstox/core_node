12) Detailed analysis of the “dynamic filename” problem
-------------------------------------------------------
The Cursor download endpoint uses redirects and produces filenames that can change:
- Cursor-<version>-x86_64.AppImage
- Cursor-<version>-x86_64.AppImage?query=...
- or other CDN path segments that are not predictable

Therefore, logic that assumes a hardcoded filename is fragile.
The robust pattern is:
- Download into a known directory
- Then search for the newest matching file with a conservative pattern
- Validate it by size (and optionally by header signatures)

Key pitfalls that must be avoided:
- Searching only for lowercase “cursor*.AppImage” while the file is “Cursor-...AppImage”
- Searching only one directory while the downloader wrote somewhere else
- Searching before the file is fully written (race)
- Using `$(...)` and printing progress to stdout (logs get captured)

13) How to validate by file content (not exit codes)
----------------------------------------------------
File verification can be layered:
13.1) Presence checks
- `[[ -f "$path" ]]` and `[[ -s "$path" ]]`

13.2) Size checks
- Cursor AppImage typically is hundreds of MB.
- A minimum threshold (e.g. 50MB) filters out HTML error pages or partial downloads.

13.3) “Magic bytes” checks (optional but stronger)
- AppImage is based on an ELF binary.
- Checking the first 4 bytes for ELF magic:
  - 0x7F 45 4C 46 (ASCII: \x7F E L F)

13.4) MIME / file type checks (optional)
- `file "$path"` contains “ELF 64-bit LSB executable” for a valid AppImage

Note:
None of these requires trusting the downloader’s exit code.
They are direct observations about the file itself.

14) Why my earlier scanning approach still failed in practice
-------------------------------------------------------------
Even with patterns like “cursor*.AppImage” and “Cursor*.AppImage”, failure can still happen if:
- The downloader saved into a different directory than the script searched.
- The download completed but the script tried to locate the file before the filesystem updated (race).
- The environment uses multiple HOME users, and the script runs under different user contexts (sudo/pkexec).

The correct approach is:
- Capture “download directory” deterministically for the exact running user context.
- Record a “pre-download snapshot” list of matching files (or newest mtime).
- After download, scan again and pick the newest file not present before.

15) The shell output discipline rule (expanded)
-----------------------------------------------
If a function returns a value with stdout and is called like:
  result="$(func)"
then:
- stdout MUST contain only the “return value”
- stderr SHOULD contain logs, progress, and debug output

Example:
- func() { echo "/path/to/file"; }    # OK
- func() { echo "downloading..."; echo "/path"; }  # BAD (stdout polluted)
- func() { echo "downloading..." >&2; echo "/path"; }  # OK

This rule alone would have prevented a large portion of the confusion.

20) Deep dive: what “download succeeded but script failed” really means
-----------------------------------------------------------------------
When a user sees the downloader report 200 OK and the file appears on disk,
yet the script prints “download failed”, the script is wrong about at least one of:
- the directory
- the filename pattern
- the timing
- the identity (which user context is running)
- the validation predicate

The script must answer these questions deterministically:
20.1) Where is the output directory?
- Is it "$HOME/Downloads" for the current user?
- Is it "/home/<user>/Downloads" for a different user?
- Is it a shared downloads dir like CORE_NODE_SHARED_DOWNLOADS?
- Is it "/tmp" because Downloads did not exist?

20.2) What is the actual created filename?
- Derived from Content-Disposition header?
- Derived from final redirect URL basename?
- Includes query string?
- Contains uppercase/lowercase differences?

20.3) When is the file “done”?
- Does the downloader write to a temp file then rename?
- Is the file still growing?
- Is the file flushed to disk when the script begins scanning?

20.4) What is the trust signal?
- file exists
- file is non-empty
- file size threshold
- ELF magic bytes
- optional “file” command detection

If any of these are guessed rather than derived, false negatives occur.

21) Deep dive: user-context issues (sudo / pkexec / root mode)
--------------------------------------------------------------
In many setups, the “Downloads directory” depends on who runs the script:
- Running as ubuntu user: $HOME = /home/ubuntu
- Running under sudo: $HOME might remain /home/ubuntu, but some tools write to /root
- Running via pkexec (GUI elevation): environment can be sanitized; HOME may differ

Therefore:
- A download can land in /home/ubuntu/Downloads
  while the elevated step scans /root/Downloads (or vice versa).

The correct design is:
- Decide download directory explicitly
- Use absolute paths
- Print both the current effective user and the resolved home directory
- Scan both the intended download_dir and the global “all Downloads” list

33) Risk analysis by section (逐段代码风险点说明)
-------------------------------------------------
This section describes typical risk points in each major area of the Cursor installer script.

33.1) Version discovery
Risks:
- API endpoints change / redirect behavior changes
- network timeouts
- partial header fetch leading to wrong filename parsing
Mitigations:
- keep a fallback (manual download path)
- do not hardcode a version unless required

33.2) Download invocation
Risks:
- downloader writes to a different dir than expected
- downloader succeeds but returns empty/incorrect “output path”
- proxy/CDN returns HTML on 200 OK
Mitigations:
- always locate by scanning the directory after download
- always validate file size and (optionally) ELF magic bytes

33.3) Candidate selection / scanning
Risks:
- pattern mismatch due to capitalization
- scanning too broadly returns wrong file (old installer)
- race condition: scanning before file is fully written
Mitigations:
- case-insensitive scan
- choose newest by mtime and/or “not present before download”
- optionally wait for size stability over short interval

33.4) File validation
Risks:
- size threshold too low rejects nothing
- size threshold too high rejects valid smaller releases (unlikely but possible)
- relying on file extension only
Mitigations:
- keep threshold conservative (50MB)
- optionally add ELF magic check for AppImage

33.5) AppImage extraction
Risks:
- extraction requires exec permission
- missing FUSE on some systems
- squashfs-root missing after extraction
Mitigations:
- chmod +x before extract
- verify squashfs-root exists after extract
- print extraction location

33.6) chrome-sandbox permissions
Risks:
- incorrect permissions break launch
- setting setuid in wrong location is a security concern
Mitigations:
- locate chrome-sandbox precisely
- apply permissions only to that file
- document why it is needed

33.7) .deb installation
Risks:
- dpkg fails due to dependencies
- apt-get fix introduces unrelated package changes
Mitigations:
- print dpkg errors clearly
- prefer minimal dependency fixes

33.8) Desktop entry creation
Risks:
- wrong user context (root vs desktop user)
- wrong icon path or missing icon
- duplicate desktop entries
Mitigations:
- detect desktop user deterministically
- verify binary exists and is executable
- disable duplicates carefully

33.9) Metadata persistence
Risks:
- saving stale path to a file that later moves
- permission issues writing to GLOBAL_VAR_DIR
Mitigations:

35) Why an AI assistant can “make code worse over time” (technical summary)
---------------------------------------------------------------------------
This section answers the practical question: “why does it feel like the AI keeps writing worse code?”
It’s not a moral issue; it is usually a process+constraints issue.

35.1) Goal drift (requirements expand mid-flight)
- When requirements change rapidly (silent vs verbose, no exit codes, full progress, refactor for brevity),
  a naive approach keeps layering new behavior on top of old behavior without a stable target.
Result:
- inconsistent UX
- duplicated logic
- larger surface area for bugs

35.2) Overfitting to the most recent failure message
- If the only signal is “it failed here”, the AI may patch around that symptom (add retries, add scans),
  rather than locating the true invariant (where the file is, and how to reliably locate it).
Result:
- complex workaround code
- fragile edge-case branches

35.3) Re-implementing existing utilities instead of reusing them
- In this repo, common_functions.sh already provides Downloads scanning helpers.
- Re-implementing scanning in the install script duplicates behavior and makes future maintenance harder.
Result:
- two sources of truth
- divergence and regressions

35.4) Output/return-value mixing in shell scripts
- Shell has a sharp edge: stdout is both “user output” and “function return channel” (via $(...)).
- If logs are printed to stdout, they can corrupt captured values.
Result:
- “it printed nothing” (logs got captured)
- “file not found” (because the variable got polluted)

35.5) Refactoring plus behavior change in one patch
- Combining “make it cleaner” with “change what it does” makes it hard to see what broke what.
Result:
- long diffs
- difficult rollbacks

35.6) Lack of a strict change budget
- Without a hard limit like “touch only 20 lines”, an AI may do broad edits to satisfy multiple objectives.
Result:
- file bloat
- higher risk of breaking unrelated logic

35.7) The correct countermeasures
- Enforce a change budget per fix (small diffs first).
- Keep behavior changes separate from refactors.
- Reuse shared helpers from common_functions.sh.
- In shell: stdout for return values, stderr for progress logs.
- Prefer “locate-after-download” using a stable, minimal candidate selection rule.

37) The exact failure mode: “download succeeded but file not found”
-------------------------------------------------------------------
This bug class usually comes from one of these mismatches:
- **Path mismatch**: downloader wrote to a directory different from what the script later scans.
- **Name mismatch**: filename differs (Cursor vs cursor, version string differs, query suffixes removed/kept).
- **Return-value mismatch**: helper returns empty/incorrect path even if the file exists.
- **Timing mismatch**: scan runs before the file is fully flushed to disk.

The minimal, reliable mitigation is:
- Determine *the* download directory used for this run.
- After download, locate the newest matching candidate *in that directory* using a broad-but-safe pattern.
- Verify the candidate by file signals (exists, size threshold; optionally ELF magic for AppImage).

45) Minimal locator algorithm (formalized)
------------------------------------------
This section formalizes the minimal algorithm used to handle dynamic filenames.

Inputs:
- download_dir (resolved once)
- patterns:
  - *cursor*.AppImage
  - *cursor*.deb
- threshold_bytes = 52428800 (50MB)

Algorithm:
1) Run download attempt into download_dir
2) Candidate selection:
   - Scan only download_dir
   - Choose newest by mtime among files matching patterns
3) Verification:
   - file exists
   - size >= threshold_bytes
   - optional: AppImage magic bytes (ELF) check
4) Use candidate path as installer file

Why “newest by mtime” works:
- The download creates/updates the file most recently.
When it can fail:
- If the directory contains a different newer file unrelated to Cursor that still matches pattern.
Mitigation:
- Keep patterns narrow: must contain “cursor”.

46) Optional strengthening (without bloat)
------------------------------------------
These are optional additions that remain small and high-signal.

46.1) ELF magic bytes verification for AppImage
- If the file ends with .AppImage, verify the first 4 bytes are ELF magic:
  - 0x7F 45 4C 46
This rejects:
- HTML pages saved as .AppImage
- random text files saved with wrong extension

46.2) “size stable” wait
- If a file is large but still downloading, size may change.
- A minimal stability check is:
  - read size, sleep 1-2 seconds, read size again
  - accept only if stable (or if size continues growing, wait limited times)

46.3) Candidate “new vs old” selection
- Record the newest candidate before download.
- After download, select newest candidate that is different from the pre-download newest.
This reduces risk of selecting an older file.

61) Bounded “size stability” wait (race condition mitigation)
-------------------------------------------------------------
If scanning occurs while the download is still being written, size can change.

61.1) Minimal bounded loop
- Read size1
- Sleep 2s
- Read size2
- If size2 == size1 and size2 >= threshold: accept
- Else repeat up to N times (e.g. N=3), then fail to manual mode

61.2) Why bounded matters
- Prevents the script from waiting forever if download is stuck.

65) Version consistency strategy (remote vs local installer vs installed)
-----------------------------------------------------------------------
This section clarifies how to decide “what to install”.

Definitions:
- remote_version: latest version detected via redirect URL filename
- installer_version: version parsed from the installer filename
- installed_version: version stored in the metadata file (or unknown)

65.1) First-time install
- If a valid installer exists in download_dir:
  - use it (prefer AppImage unless policy says otherwise)
- Else:
  - attempt auto-download
  - if still no valid installer, enter manual download flow

65.2) Upgrade install
- If installed_version == remote_version:
  - do nothing
- If installed_version != remote_version:
  - prefer installing an installer whose installer_version == remote_version
  - if only an older installer is available, treat as fallback and require confirmation

65.3) Why file-signal verification comes before version checks
- A corrupted or partial file must be rejected regardless of version strings.
- Version comparisons only matter after a file is proven plausible.

66) Safe deletion strategy (no wildcards)
-----------------------------------------
Deletion is the highest-risk operation in an installer script.

66.1) Allowed delete

66.2) Disallowed delete
- Any wildcard delete in Downloads (e.g., rm -f ~/Downloads/cursor*.AppImage) unless operator explicitly confirms.
- Any recursive delete that touches user directories.

66.3) Principle
- “Keep old installers until the new one is verified and installed.”
