12) Detailed analysis of the “dynamic filename” problem
-------------------------------------------------------
The Cursor download endpoint uses redirects and produces filenames that can change:
- Cursor-<version>-x86_64.AppImage
- Cursor-<version>-x86_64.AppImage?query=...
- or other CDN path segments that are not predictable

Therefore, logic that assumes a hardcoded filename is fragile.
The robust pattern is:
- Download into a known directory
- Then search for the newest matching file with a conservative pattern
- Validate it by size (and optionally by header signatures)

Key pitfalls that must be avoided:
- Searching only for lowercase “cursor*.AppImage” while the file is “Cursor-...AppImage”
- Searching only one directory while the downloader wrote somewhere else
- Searching before the file is fully written (race)
- Using `$(...)` and printing progress to stdout (logs get captured)

13) How to validate by file content (not exit codes)
----------------------------------------------------
File verification can be layered:
13.1) Presence checks
- `[[ -f "$path" ]]` and `[[ -s "$path" ]]`

13.2) Size checks
- Cursor AppImage typically is hundreds of MB.
- A minimum threshold (e.g. 50MB) filters out HTML error pages or partial downloads.

13.3) “Magic bytes” checks (optional but stronger)
- AppImage is based on an ELF binary.
- Checking the first 4 bytes for ELF magic:
  - 0x7F 45 4C 46 (ASCII: \x7F E L F)

13.4) MIME / file type checks (optional)
- `file "$path"` contains “ELF 64-bit LSB executable” for a valid AppImage

Note:
None of these requires trusting the downloader’s exit code.
They are direct observations about the file itself.

14) Why my earlier scanning approach still failed in practice
-------------------------------------------------------------
Even with patterns like “cursor*.AppImage” and “Cursor*.AppImage”, failure can still happen if:
- The downloader saved into a different directory than the script searched.
- The download completed but the script tried to locate the file before the filesystem updated (race).
- The environment uses multiple HOME users, and the script runs under different user contexts (sudo/pkexec).

The correct approach is:
- Capture “download directory” deterministically for the exact running user context.
- Record a “pre-download snapshot” list of matching files (or newest mtime).
- After download, scan again and pick the newest file not present before.

15) The shell output discipline rule (expanded)
-----------------------------------------------
If a function returns a value with stdout and is called like:
  result="$(func)"
then:
- stdout MUST contain only the “return value”
- stderr SHOULD contain logs, progress, and debug output

Example:
- func() { echo "/path/to/file"; }    # OK
- func() { echo "downloading..."; echo "/path"; }  # BAD (stdout polluted)
- func() { echo "downloading..." >&2; echo "/path"; }  # OK

This rule alone would have prevented a large portion of the confusion.

20) Deep dive: what “download succeeded but script failed” really means
-----------------------------------------------------------------------
When a user sees the downloader report 200 OK and the file appears on disk,
yet the script prints “download failed”, the script is wrong about at least one of:
- the directory
- the filename pattern
- the timing
- the identity (which user context is running)
- the validation predicate

The script must answer these questions deterministically:
20.1) Where is the output directory?
- Is it "$HOME/Downloads" for the current user?
- Is it "/home/<user>/Downloads" for a different user?
- Is it a shared downloads dir like CORE_NODE_SHARED_DOWNLOADS?
- Is it "/tmp" because Downloads did not exist?

20.2) What is the actual created filename?
- Derived from Content-Disposition header?
- Derived from final redirect URL basename?
- Includes query string?
- Contains uppercase/lowercase differences?

20.3) When is the file “done”?
- Does the downloader write to a temp file then rename?
- Is the file still growing?
- Is the file flushed to disk when the script begins scanning?

20.4) What is the trust signal?
- file exists
- file is non-empty
- file size threshold
- ELF magic bytes
- optional “file” command detection

If any of these are guessed rather than derived, false negatives occur.

21) Deep dive: user-context issues (sudo / pkexec / root mode)
--------------------------------------------------------------
In many setups, the “Downloads directory” depends on who runs the script:
- Running as ubuntu user: $HOME = /home/ubuntu
- Running under sudo: $HOME might remain /home/ubuntu, but some tools write to /root
- Running via pkexec (GUI elevation): environment can be sanitized; HOME may differ

Therefore:
- A download can land in /home/ubuntu/Downloads
  while the elevated step scans /root/Downloads (or vice versa).

The correct design is:
- Decide download directory explicitly
- Use absolute paths
- Print both the current effective user and the resolved home directory
- Scan both the intended download_dir and the global “all Downloads” list

33) Risk analysis by section (逐段代码风险点说明)
-------------------------------------------------
This section describes typical risk points in each major area of the Cursor installer script.

33.1) Version discovery
Risks:
- API endpoints change / redirect behavior changes
- network timeouts
- partial header fetch leading to wrong filename parsing
Mitigations:
- keep a fallback (manual download path)
- do not hardcode a version unless required

33.2) Download invocation
Risks:
- downloader writes to a different dir than expected
- downloader succeeds but returns empty/incorrect “output path”
- proxy/CDN returns HTML on 200 OK
Mitigations:
- always locate by scanning the directory after download
- always validate file size and (optionally) ELF magic bytes

33.3) Candidate selection / scanning
Risks:
- pattern mismatch due to capitalization
- scanning too broadly returns wrong file (old installer)
- race condition: scanning before file is fully written
Mitigations:
- case-insensitive scan
- choose newest by mtime and/or “not present before download”
- optionally wait for size stability over short interval

33.4) File validation
Risks:
- size threshold too low rejects nothing
- size threshold too high rejects valid smaller releases (unlikely but possible)
- relying on file extension only
Mitigations:
- keep threshold conservative (50MB)
- optionally add ELF magic check for AppImage

33.5) AppImage extraction
Risks:
- extraction requires exec permission
- missing FUSE on some systems
- squashfs-root missing after extraction
Mitigations:
- chmod +x before extract
- verify squashfs-root exists after extract
- print extraction location

33.6) chrome-sandbox permissions
Risks:
- incorrect permissions break launch
- setting setuid in wrong location is a security concern
Mitigations:
- locate chrome-sandbox precisely
- apply permissions only to that file
- document why it is needed

33.7) .deb installation
Risks:
- dpkg fails due to dependencies
- apt-get fix introduces unrelated package changes
Mitigations:
- print dpkg errors clearly
- prefer minimal dependency fixes

33.8) Desktop entry creation
Risks:
- wrong user context (root vs desktop user)
- wrong icon path or missing icon
- duplicate desktop entries
Mitigations:
- detect desktop user deterministically
- verify binary exists and is executable
- disable duplicates carefully

33.9) Metadata persistence
Risks:
- saving stale path to a file that later moves
- permission issues writing to GLOBAL_VAR_DIR
Mitigations:
- save only stable paths
- include version and size
