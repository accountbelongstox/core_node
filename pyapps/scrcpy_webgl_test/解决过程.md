  🔬 技术亮点

  1. 基于QtScrcpy的Shader实现

  // Fragment shader (与QtScrcpy qyuvopenglwidget.cpp完全相同)
  const vec3 Rcoeff = vec3(1.1644,  0.000,  1.7927);
  const vec3 Gcoeff = vec3(1.1644, -0.2132, -0.5329);
  const vec3 Bcoeff = vec3(1.1644,  2.1124,  0.000);

  yuv.x = texture2D(textureY, textureOut).r - 0.0625;
  yuv.y = texture2D(textureU, textureOut).r - 0.5;
  yuv.z = texture2D(textureV, textureOut).r - 0.5;

  rgb.r = dot(yuv, Rcoeff);
  rgb.g = dot(yuv, Gcoeff);
  rgb.b = dot(yuv, Bcoeff);

  2. YUV推流协议

  [1B] serial_length
  [NB] serial
  [8B] pts
  [2B] width
  [2B] height
  [4B] y_size, u_size, v_size (各4B)
  [YB] Y平面
  [UB] U平面
  [VB] V平面

● 根据文档分析，H.264编码是scrcpy架构中不可避免的，但前端WebGL 不需要处理H.264！让我解释一下：

  📊 数据流程架构

  Android设备 (必须H.264) → 网络传输 (H.264) → 后端解码 (YUV) → 前端WebGL渲染 (YUV)
       ↑                                                                    ↑
    无法绕过                                                        只处理YUV数据

  为什么Android端必须使用H.264？

  1. Android系统限制：MediaProjection API → MediaCodec硬件编码器 → 输出H.264
  2. 带宽要求：
    - 原始YUV: 1080p@30fps = ~90 MB/s （无法传输）
    - H.264编码: ~1.5 MB/s （压缩60倍）

  前端WebGL的优势 ✅

  前端完全不处理H.264！ 收到的是已解码的YUV数据：
  - ✅ 直接接收YUV三个平面（Y/U/V）
  - ✅ GPU着色器进行YUV→RGB转换
  - ✅ 无需WebCodecs API或MSE
  - ✅ 浏览器兼容性最好
