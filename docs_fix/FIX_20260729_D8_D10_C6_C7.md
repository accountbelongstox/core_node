## 8.1 / 8.3 / 9 / 6 — RPC v2 "Backend unreachable" + 30000ms timeouts (root cause)

The symptom set (Queue overview unavailable, `RPC timeout after 30000ms` on
unrelated routes, UI-connected-before-backend stalls) had ONE mechanism:
**the uvicorn event loop was being blocked**, violating RPC v2 standard §6
("the WebSocket receive loop stays responsive") and the contract documented in
`_serialized_bridge.py` ("if the loop blocks on serialized calls, every route
times out together"). `StateRepository` runs SQLite with
`busy_timeout=30000`, so each on-loop DB call could freeze the whole RPC
layer for up to 30s — matching the client-side 30s timeouts exactly.

Blocking call sites found and fixed:

- `server/ack_manager.py` — every durable delivery/ACK path called the
  `@serialized_method` RequestEvent/Inventory tables **synchronously on the
  loop** (`notify_websocket_with_retry`, `_send_websocket_notification`,
  `_check_websocket_ack_timeout`, `handle_ack`,
  `prepare_http_response_with_ack`, `_store_in_inventory`). All converted to
  coroutines routed through `await_serialized`.
- `server/websocket_handler.py` — `RpcDeliveryService` SQLite calls
  (`get_client_offset` ×3, `ack_event`, `replay_unacked`) ran directly on the
  loop; now `asyncio.to_thread` (same pattern as the existing
  `authenticate_client_session`). `_deliver_durable_events` is now awaited.
  ACK/notify call sites updated for the async ack_manager (`create_task` for
  fire-and-forget delivery, `await` for the legacy ACK path).
- `server/rpc_delivery_service.py` — `_send_frame` did the
  `mark_delivery_sent` SQLite write on the loop after every durable send;
  now `asyncio.to_thread`.
- `server/sse_broadcaster.py` — `publish()` did `insert_system_event` on the
  loop **once per broadcast, including every `pycore_log` line** (the hottest
  blocking path in the server). Now a coroutine with the DB insert offloaded;
  `fastapi_server.broadcast_event` awaits it.
- `server/request_processor.py` — non-coroutine durable-route handlers ran
  **directly on the loop**; now `asyncio.to_thread`, mirroring the WS
  sync-route path.
- `server/http_handler.py` — `prepare_http_response_with_ack` was wrapped in
  `await_serialized`, which ran it on a bridge pool thread where
  `asyncio.get_running_loop()` raises — **every async HTTP route answered
  500** (reproduced live: `POST /rpc/ui.task_center.get_queue_center_snapshot`
  → 500 in 0.14s). Now a plain `await` of the coroutine version.

Callers verified: `_wrap_idempotent_notify` already branches on
`iscoroutinefunction`; `sse_broadcaster.publish` has exactly one caller.

## 6.1 / 8.1 — backend tasks must not run without an explicit UI enable

Root cause: `assist_capability_enabled()` returned the Config/env
`legacy_default` (translation worker: `"1"`) whenever the `assist_laravel`
section was absent, so a fresh boot processed queue work the user never
switched on.

- `pycore/pyctl/assist/assist_settings.py` — section ABSENT now means OFF for
  every lane (`legacy_default` ignored in that branch; env flags survive only
  as hard kill-switches). Section PRESENT keeps the existing
  `enabled AND capability` rule, so boot restores exactly the persisted UI
  intent. Docstrings updated (also `sentence_audio_auto.py`).
- The save side was already aligned: Queue Center toggles persist via
  `assist_config` / `apply_*_auto_start` and apply live via
  `assist_capability_sync.apply_assist_runtime`; `global_task_worker` stays
  always-on as the transport but claims nothing while its lane gates are off.

## 8.2 — Laravel endpoint reset after restart

Backend persistence (`user_data.json` → `laravel_api.current`) was already
atomic and sound; the frontend kept **no copy**, so any backend-side reset
was unrecoverable. Per the requirement both sides now store the selection and
the FRONTEND wins on connect:

- `PcLaravelEndpointContext.tsx` — FE copy in localStorage
  (`pycore_laravel_current_endpoint`), written on `select()` and on the
  `laravel_endpoint_changed` broadcast; after every successful
  `laravel_api.list` a mismatch pushes `laravel_api.select(feUrl)` once
  (one-shot guard, failure re-arms).
- `laravel_endpoint_manager.py` — module docstring now records the dual-store
  / frontend-wins rule in code, as required.

## 7 — 409 "task reassigned / not ours" result drops

Root cause (not the 409 handler, which already drops correctly): a long task
— cold qwen3tts start, a large word batch — outlives Laravel's `timeout_at`
lease; `releaseTimedOutTasks` reassigns it and the late result is rejected,
wasting the work.

- pycore `translation_worker/worker.py` — `_start_lease_keepalive`: each
  dispatched task gets a THREAD_BUS-based keep-alive thread (condition wait,
  no sleep-poll) that pings `processing` at `lease/3` (clamped 15–120s) with
  **no progress field** until `_process_task` finishes.
- laravel_main — `WorkerController::submitResult` +
  `TaskManagerService::submitResult` accept `?float $progress = null`; a null
  progress (keep-alive ping) extends the lease **without** resetting stored
  progress to 0. Existing float callers unaffected (`php -l` OK).

## 6.2.2 — Task TAB "● RUNNING Stop" had no effect

Root cause: `stop` was serialized on `lifecycleQueue` behind
`startAll`/`restore`, and a start against a dead endpoint blocks inside
`BaseApiClient.request` (default backend timeout **10 min** × 4 attempts), so
Stop — the escape hatch — could never run.

- `task-center-listener.ts` — new `runStopAction`: preemptive (never joins
  `lifecycleQueue`), bumps `runtimeEpoch`, tears down
  taskCenter/validity/bing/run-intent immediately.
- Epoch guards: `handleStart` and `handleSetCapability` capture the epoch and
  roll back instead of resurrecting when a Stop landed mid-start;
  `runLifecycleAction` drops an action that was still queued when a Stop
  landed.
- Start flow unchanged: popup sends `activeCapabilities`, background maps them
  to processors and claims from Laravel, per the checked features.
