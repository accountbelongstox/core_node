   ## 3.2 Relay protocol (v1)
   1. UI -> Laravel: `POST /api/relay/{machineId}/requests`
      `{ method, path, headers?, body_ref? }` where large
 bodies were first
      `POST /api/relay/{machineId}/blobs` (chunked) ->
 `body_ref`. Laravel:
      - verifies the pair gate in the REGISTRY (machine
 heartbeat fresh AND the
        UI session's pair registration fresh) else **HTTP
 409 `peer-offline`
        immediately** (R3, A2);
      - stores the request (QueueCenterCacheStore-family
 store, short TTL);
      - publishes a small `relay.request` update
 `{request_id, method, path,
        size}` on `pycore.pair.{machineId}`
 (`mercure_publish()`, private).
   2. pycore relay consumer (in its SSE consumer thread)
 wakes on
      `relay.request` - or on its bounded poll (400 ms) -
 fetches
      `GET /api/relay/{machineId}/requests/{request_id}`
 (body included when
      small; blob refs fetched via `GET .../blobs/{ref}`),
 executes it against
      `127.0.0.1:59000` through the existing local HTTP
 stack (route contract
      untouched - R6), then `POST
 /api/relay/{machineId}/responses`
      `{request_id, status, headers, body | body_ref}`.
   3. UI receives the response either on the pair topic
 (`relay.response`
      `{request_id, status, size}` wake update) or by its
 in-flight HTTP poll
      `GET
 /api/relay/{machineId}/responses/{request_id}?wait=1`
 (long-poll,
      bounded ~25 s). v1 ships the long-poll (simpler, no UI
 callback routing);
      the wake update stays as the latency optimization
 hook.
   4. Timeouts: request TTL 60 s; no store-and-forward
 across offline peers (the
      pair REFUSES when offline - b.txt's offline-message
 branch is deliberately
      NOT taken for interactive RPC; offline work already
 belongs to Queue
      Center tasks).

 inline JSON body
      <= 256 KB, blob chunks <= 4 MB, per-request total <=

      (terminal/code-sync/audio bounded accordingly).

   ### Mercure (mercure.rocks spec;
 frankenphp.dev/docs/mercure) - BINDING transport
   - Protocol shape: publish/subscribe over plain HTTP.
 Downstream = **SSE**:
     `GET /.well-known/mercure?topic=...` (repeatable
 `topic` params, native
     `EventSource` in browsers, automatic reconnect with
 `Last-Event-ID`
     header). Upstream = authenticated `POST
 /.well-known/mercure` (form
     fields `topic`, `data`, `private`, `id`, `type`,
 `retry`).
   - Auth (v0.x, which is what the FrankenPHP-embedded hub
 implements):
     HMAC JWTs with a `mercure` claim -
 `{"mercure":{"publish":["*"]}}` for
     publishers (Authorization: Bearer on POST),
 `{"mercure":{"subscribe":
     ["<topic>"]}}` for subscribers of PRIVATE updates
 (browser EventSource
     cannot set headers -> the short-lived token is set as
 the hub's
     authorization COOKIE by our auth endpoint; native
 clients use the
     Authorization header). A PRIVATE update is delivered
 only when the
     subscriber's token grants `subscribe` on at least one
 of its topics -
     topic matching alone never grants delivery. Without
 `anonymous`, the
     hub accepts no unauthenticated subscriptions at all.
   - The mercure.rocks spec shown as latest is the 1.0 ALPHA
 (OAuth
     authorization_details model, `match`/`aud` etc.); the
 DEPLOYED hub
     implements the stable v0.x line (`topic` param +
 `mercure` claim). This
     design binds ONLY to v0.x features; the alpha is
 recorded so the v1.x
     upgrade path is known, not followed (norm: latest
 STABLE spec of what
     actually ships in the binary).
   - FrankenPHP integration (official doc): Caddyfile
 `mercure { publisher_jwt
     ... subscriber_jwt ... [anonymous] }`;
 `mercure_publish(topics, data,
     private, id, type, retry)` PHP function publishing to
 the built-in hub
     in-process (no HTTP hop, no token handling in app
 code); hub POST with a
     signed JWT as the runtime-independent alternative;
 Symfony Mercure
     component optional. Under Octane the block rides
 `config/octane.php`
     (0.2).
   - Presence: NONE in the protocol (no roster, no
 join/leave). The
     subscription API (`GET
 /.well-known/mercure/subscriptions`) + subscription
     events expose connection-tracking data but are an
 opt-in hub feature and
     experimental - this design does NOT build on them;
 RelayMachineRegistry
     is the roster authority.
   - Fit for this feature: SSE downstream + HTTP-POST
 upstream is EXACTLY the
     relay shape (outbound-only machine, no inbound holes);
 SSE is plain HTTP
     so it rides the same h3 listener - the
 WebSocket-over-QUIC browser gap
     (RFC 9220) that forced the old wss exception disappears
 entirely.

 Key technical content for the new Mercure research
 subsection (2.2):
 ### Mercure (mercure.rocks spec +
 frankenphp.dev/docs/mercure)
 - Protocol: pub/sub over plain HTTP. Subscribe = native
   EventSource GET with ?topic= (repeatable); delivery =
   Server-Sent Events (text/event-stream); Publish =
   authenticated HTTP POST (form: topic, data, private, id,
   type, retry) to the hub URL; works with any HTTP version
   incl. h3 (no upgrade handshake).
 - Version reality: the hub embedded in FrankenPHP
   implements the STABLE v0.x line (topic query param; JWT
   mercure claim). The mercure.rocks 1.0-alpha draft (OAuth2
   RFC9396 authorization details, RFC9728 metadata, match_*
   params) is NOT deployed by it; spec itself notes
   pre-standardization hubs don't publish protected-resource
   metadata. Design targets v0.x semantics; client library
   isolates the delta.
 - Auth (v0.x): publisher = Bearer JWT signed with
   publisher_jwt key carrying
   {"mercure":{"publish":["..."]}}; subscriber =
   mercureAuthorization HttpOnly cookie (browsers;
   EventSource cannot set headers) or Authorization Bearer
   (non-browser) carrying {"mercure":{"subscribe":["..."]}};
   private updates (published with private=1) delivered only
   to subscribers whose token matches the topic; anonymous
   option allows JWT-less subscription to public updates
   only.
 - FrankenPHP hub: Caddyfile mercure { publisher_jwt <key>;
   subscriber_jwt <key>; [anonymous] }; hub at
   /.well-known/mercure on the same 443 site (b.txt's
   http://127.0.0 sample is wrong); publish in-process via
   mercure_publish(string|array $topics, string $data='',
   bool $private=false, ?string $id=null, ?string
   $type=null, ?int $retry=null): string; or POST with
   publisher JWT; symfony/mercure component
   (LcobucciFactory) issues JWTs + subscriber cookies.
 - Reliability: SSE auto-reconnect with Last-Event-ID; hub
   offers reconciliation (EventStore replay) — project relay
   does NOT depend on hub replay (HTTP store-and-fetch is
   the data plane); subscription API GET
   /.well-known/mercure/subscriptions + subscription events
   exist (experimental) but hub subscriber IDs are random
   per connection — usable for diagnostics only, NOT a
   roster.
 - Presence gap (binding): Mercure has NO server-side
   membership truth; the both-ends-online gate stays the
   RelayMachineRegistry heartbeat design. (Matches 0.2.)
 And SSE vs WS note: SSE is plain HTTP → rides HTTP/2/3
 multiplexing; no RFC-9220 exception; the UI's realtime leg
 gains h3.
