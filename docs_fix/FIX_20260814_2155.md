# Pycore Native Terminal Window Control

Date: 2026-08-14 21:55

Status: Applied; static source review complete, runtime verification pending
user-run

Scope: Pycore, Pycore Manager UI, Windows 10/11, and Linux X11 desktops on
Ubuntu, Debian, Kali, and compatible distributions

## Objective

Pycore Manager now provides one real-time control surface for visible terminal
windows. It discovers supported terminal applications, preserves their desktop
coordinates, raises and physically clicks a selected window, submits clipboard
text through native input, captures in-memory previews, and keeps per-terminal
drafts, view state, and submission history.

The implementation follows these boundaries:

1. Window activation is based on the native window identifier and rectangle.
2. Every focus-sensitive action raises and physically clicks the terminal first.
3. Windows and Linux implementations load only on their matching platform.
4. Shared window primitives, terminal identifiers, state storage, and UI panels
   have one owner each.
5. Terminal content is persisted and transported as raw text rather than being
   embedded in JSON state records.
6. Screenshots stay in memory and are never written to a cache directory.

## Terminal Discovery

Terminal recognition is centralized in
`pycore/pyutils/common/terminal_identifiers.py`.

Windows discovery combines visible top-level Win32 windows with known process
names and classes. It covers Windows Terminal, Console Host, CMD, PowerShell,
WSL distribution launchers, PuTTY, mintty, ConEmu, Cmder, WezTerm, Alacritty,
Kitty, Tabby, and other registered terminal hosts.

Linux discovery parses the X11 window list returned by `wmctrl -l -p -G -x` and
matches centralized terminal class tokens. It covers GNOME Terminal, GNOME
Console, Konsole, XTerm, UXTerm, XFCE Terminal, QTerminal, Tilix, Terminator,
Alacritty, Kitty, WezTerm, Foot, Guake, and related terminal emulators.

The Linux backend requires an interactive X11/Xorg session with `DISPLAY`,
`wmctrl`, and `xdotool`. Wayland does not expose the required common global
window enumeration and physical-input contract, so the backend reports an
explicit unsupported capability instead of silently using another control
method.

## Centralized Platform Architecture

`pycore/pyctl/terminal/terminal_service.py` conditionally imports only
`windows_terminal_backend` on Windows or `linux_terminal_backend` on Linux.
Unsupported systems keep the service available but return a structured
`unsupported_platform` result.

`pycore/pyutils/window/terminal_backend.py` defines the shared backend protocol,
scroll modes, and page-size calculation. Platform backends implement only their
native details.

All reusable Win32 calls are owned by `pycore/pyutils/window/ops.py`, including:

- window enumeration and process lookup;
- `get_window_thread_process_id`;
- restore-without-activation and rectangle reads;
- temporary topmost state and foreground raising;
- physical screen-coordinate clicks;
- native key and key-combination input;
- native mouse-wheel input and system wheel-line lookup.

This removes the earlier duplicate definitions that caused backend imports such
as `get_window_thread_process_id` to diverge from the shared operation library.

## Activation Contract

Every activation resolves the current terminal window and its latest rectangle.

On Windows, Pycore:

1. Restores a minimized window without activating it.
2. Records whether the window was already topmost.
3. Temporarily uses `SetWindowPos(HWND_TOPMOST)`, `BringWindowToTop`, and
   foreground activation as compatible raise paths.
4. Reads the rectangle again after the raise.
5. Moves the real pointer to the window center and sends a physical left click
   through `SendInput`.
6. Removes the temporary topmost flag when Pycore added it.

On Linux X11, Pycore:

1. Maps the window with `xdotool windowmap --sync`.
2. Attempts activation through both `wmctrl -i -a` and
   `xdotool windowactivate`.
3. Raises it with `xdotool windowraise`.
4. Reads the window list and rectangle again after the raise.
5. Moves the pointer to the center and sends X11 button 1.

This same activation contract runs before command-history navigation, terminal
scrolling, and text submission.

## Real-Time Window Canvas and Screenshots

The Terminal windows tab is implemented in
`poly_apps/pycore_laravel_wordnew_ui/apps/pycore-manager/pages/PcTerminalPage.tsx`.

The UI does not render terminals as a packed list. It calculates the desktop
bounds, retains negative and multi-monitor coordinates, and draws every window
at its proportional desktop position and size. Overlapping native windows also
overlap on the canvas.

Each live window is captured every two seconds through the shared screen-capture
component. The capture reads the native window rectangle, downsizes the image
for transport, encodes it as PNG in memory, and returns Base64 directly to the
UI. No screenshot is retained on disk. The terminal title remains outside and
above the image so it is readable even when the screenshot is dark or busy.

Clicking a preview opens the current live screenshot. The large preview updates
from the same snapshot stream instead of freezing the frame that opened it.

## Stable Terminal Numbers and Text State

`pycore/pyctl/terminal/terminal_state_repository.py` assigns a monotonically
increasing terminal number on first discovery. The identity combines platform,
native window identifier, process identifier, and class. Reconciliation reuses
that number while the identity remains available.

State is stored under:

`APP_DATA_DIR/terminal_windows`

`pycore/pyutils/common/flat_text_store.py` stores one key per `.txt` filename and
the raw value as file content. Representative files are:

```text
next_number.txt
terminal.000001.draft.txt
terminal.000001.preview_expanded.txt
terminal.000001.log.<log_id>.content.txt
terminal.000001.log.<log_id>.title.txt
terminal.000001.log.<log_id>.date.txt
terminal.000001.log.<log_id>.status.txt
terminal.000001.log.<log_id>.error_code.txt
```

Draft and log bodies are not placed in one JSON document. Directory scanning
loads short metadata and content sizes; a selected draft or log body is read
from its text file only when requested. Long text and text that itself contains
JSON therefore remain ordinary raw content.

If a numbered terminal closes but still has a draft, submission history, or an
expanded-preview state, the UI keeps a dashed offline window at its last known
coordinates. It preserves the saved state without pretending that native
operations are available.

## Shared Operation Panel

The normal right-side operation area and the expanded large-preview operation
area call the same `renderOperationPanel` function. They share the same selected
terminal, draft, draft-save state, action handlers, history selection, and raw
log content. There is no second modal-specific command state.

The large-preview bottom-right control expands or collapses the shared panel.
Expanded state is saved per stable terminal number in
`terminal.<number>.preview_expanded.txt`; reopening the same terminal restores
the previous state. The overlay occupies the right half of the preview and uses
a translucent, blurred background so the screenshot remains visible.

Clicking the uncovered screenshot converts the click from the displayed
`object-contain` image rectangle into normalized image coordinates. The backend
then raises the terminal, reads its current native rectangle, maps the ratios to
screen coordinates, and performs a physical click at that point.

## Input and Submission

Input uses this fixed sequence:

1. Persist a pending per-terminal history record.
2. Back up the current system clipboard text.
3. Copy the requested terminal text into the clipboard.
4. Raise and physically left-click the selected terminal.
5. Move to the current window center and physically right-click to paste.
6. Send native Enter.
7. Restore the original clipboard text.
8. Complete the history record with sent or failed status.

The draft is automatically stored per terminal, including unsent text. Selecting
another terminal swaps to that terminal's draft and history. Submission content
uses `text/plain`; only small route metadata uses the normal structured request.

## Command-History Controls

The shared panel exposes Previous command and Next command buttons with up and
down arrows. Both first run the complete activation contract and then send a
native Up or Down key to the focused terminal.

Windows uses the shared `press_native_key` Win32 input primitive. Linux uses
`xdotool key Up` or `xdotool key Down` after X11 activation and the physical
center click.

## Page Scrolling and Immediate Delayed Capture

The shared panel also exposes Page up, Page down, and To bottom.

Page operations follow this sequence:

1. Raise, activate, and physically click the current terminal.
2. Calculate the visible terminal rows from the current window height.
3. Convert one viewport into native wheel steps.
4. Scroll exactly one calculated page upward or downward.
5. Wait 280 milliseconds for the terminal to render.
6. Capture only the affected terminal window in memory.
7. Return that screenshot in the action response.
8. Immediately replace the UI screenshot in both the canvas and open large
   preview, without waiting for the next two-second poll.

Windows reads `SPI_GETWHEELSCROLLLINES` and sends
`MOUSEEVENTF_WHEEL` through the centralized `SendInput` wrapper. Linux uses X11
wheel buttons 4 and 5 through xdotool with the same viewport-derived step count.

To bottom is kept bounded and immediate:

- Windows Terminal uses its native `Ctrl+Shift+End` scroll-to-bottom action.
- Other Windows terminal hosts use a large native wheel movement as fallback.
- Linux terminal emulators use the standard `Shift+End` scroll-to-bottom action.

All three operations return the same delayed in-memory screenshot contract.

## HTTP Routes

Backend and frontend route names are centralized in
`pycore/callmodule/rpc_routes/route_names.py` and
`core/api-libs/pycore/PycoreHttpRoutes.ts`.

| Route | Method | Purpose |
|---|---|---|
| `ui/terminal/windows` | POST | Reconcile windows, state, and live screenshots |
| `ui/terminal/activate` | POST | Raise and click a terminal |
| `ui/terminal/click` | POST | Raise and click a normalized screenshot position |
| `ui/terminal/command_history` | POST | Activate, then send Up or Down |
| `ui/terminal/scroll` | POST | Activate, scroll, delay, and return a screenshot |
| `ui/terminal/draft` | POST `text/plain` | Save one terminal draft |
| `ui/terminal/input` | POST `text/plain` | Submit raw terminal content |
| `ui/terminal/view` | POST `text/plain` | Save expanded-preview state |
| `ui/terminal/content` | GET `text/plain` | Read one draft or log body |

`pycore/pyutils/rpc_v2/server.py` merges query metadata with a raw
`text/plain` request body, so terminal content does not depend on JSON parsing
or JSON body-size behavior.

## Failure Contract

Native failures return stable error codes that the UI maps through i18n. The
contract distinguishes unsupported sessions, enumeration failures, missing
windows, restore/raise failures, coordinate failures, pointer/click failures,
history-key failures, scroll failures, delayed screenshot failures, clipboard
failures, and Enter failures.

Offline saved windows disable native controls while keeping their drafts and
history readable.
