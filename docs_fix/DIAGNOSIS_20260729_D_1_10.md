# d.txt 1–10 静态问题排查报告

日期：2026-07-29

范围：`docs_fix/origin/d.txt` 第 1–10 项，覆盖 Pycore、Pycore UI、WordNew、Laravel Main 与 MCP Chrome。

边界：本报告只记录问题，不包含修复；未修改源代码，未运行构建、测试或服务。

## 总结

静态排查确认的主要高风险问题包括：

- Agent History 自动处理会提前推进最新游标，可能跳过旧批次。
- Laravel 上传失败仍会把 Agent History operation 标记为成功。
- Laravel 任务租约可能在执行器仍运行时过期并重新分配，最终产生 409 并丢弃旧结果。
- 多项 Pycore 后台 transport/monitor 默认启用，与 UI 显式开关不一致。
- Queue Center 在 UI 先启动、后端后启动时没有基于 WS welcome 的立即恢复机制。
- MCP Chrome Stop 只停止本地轮询，不向 Laravel 取消或释放任务。
- Qwen3TTS 端口回收没有验证进程身份，可能误杀合法服务。

## 1. AgentHistoryArticle `time` 未定义

当前两套相关实现均已经导入 `time`：

- `pycore/callmodule/services/agent_history_pipeline/audio_stage.py:3`
- `pycore/callmodule/services/agent_history_article_service.py:10`

因此 `pipeline tick error: name 'time' is not defined` 无法由当前源码直接产生。该日志更可能来自未重启的旧进程、旧部署文件或旧模块快照。

同时，项目仍保留旧版 `agent_history_article_service.py` 和新版 `agent_history_pipeline/` 两套实现，增加了运行版本及问题归属混淆风险。

## 2. Agent History 与 Daily Reading

### 2.1 工具勾选与提示词显示

- `agent_history_pipeline/config.py:25-45` 中 `enabled_tools` 默认仍为空数组，并非全部勾选。
- `PcAgentHistoryToolCheckboxes.tsx:45-52` 只对勾选工具执行提取测试，没有把勾选范围与提示词页面的显示范围绑定。
- 页面加载时会同时启动所有已勾选工具的 `test_extract`，没有并发限制。
- Auto Process 关闭时，勾选项可以继续触发 extractor heartbeat，但提示词显示仍读取统一 index/prompts，不是明确的“仅勾选工具监控视图”。

### 2.2 自动处理队列可能跳过旧历史

普通启用流程只调用 `save_config()`，不会调用完整的 `start_backfill()`。

`agent_history_pipeline/worker.py:179-208` 在没有活动 operation 时：

1. 从 newest-first 计划中只取 `items[0]`；
2. `_process_item()` 在该次 tick 只完成第一阶段；
3. 随后却无条件调用 `_advance_cursor_for_input(items[0])`；
4. 游标因此提前移动到最新批次尾部；
5. 尚未纳入 operation 的旧批次会被之后的 `after_ts` 排除。

显式 `start_backfill()` 会一次创建全部批次，但 UI 注释及普通 Auto Process 路径明确不调用该入口。因此普通开启存在历史批次遗漏风险。

### 2.3 Generation Records 与 Laravel 上传

- 当前 Generation Records 已经直接展示英文和中文正文，不再必须点击 Show full text。
- `worker.py:353-385` 捕获 Laravel 上传异常后，仍把 item 标记为 `succeeded/completed` 并推进工具游标。
- 这会造成 UI 显示完成，但 Laravel 和 Daily Reading 没有对应记录。
- `agent_history_article_records.py:99` 把 `reference_cn` 截断到 2000 字符；延迟上传只能读取这个截断版本。
- 延迟上传时 `raw_text` 传空字符串，原始 preview/word count 信息丢失。
- `mark_uploaded()` 只保存 `uploaded/uploaded_at`，没有保存 Laravel 返回的 `article_id`、`source_key` 和 `audio_url`。

### 2.4 Daily Reading 显示与播放器路由

Laravel 当前已具备以下写入链路：

- 创建英文 Daily Reading article；
- 保存中文参考文；
- 保存音频；
- 创建 Daily Reading document；
- 发送 `article.published`。

对应代码位于 `AppQyV1ArticleController.php:639-763`。当前主要断点在 Pycore 上传失败被标记为完成。

WordNew 会把 URL 改为 `#/read-daily/${articleId}`，但播放器仍由 `WfDailyReadingPlayerOverlay` 覆盖在同一 Daily Reading 组件上，不是独立的播放器页面。

### 2.5 最新提示词与公平处理

Planner 已实现每个工具 newest-first 和工具间 round-robin，但普通 Auto Process 的提前游标推进会破坏 backlog 完整性。最新内容能够被优先选中，但旧内容可能被永久跳过。

### 2.6 Word Groups 联动

`WfDailyReadingWordGroupsPanel.tsx` 当前只对 Default Vocabulary Group 计算文章单词的 `inDefault/played/new` 关系。

其他 Word Groups 仅显示名称和总词数，没有显示：

- 当前文章命中了该组的哪些单词；
- 每组命中数量；
- 播放、已学和未分组状态；
- 文章与所有词组的逐组关系。

## 3. 子应用路由与网络生命周期

React Router 会卸载非活动子应用，但无法满足“只有活动子应用有网络”的完整要求：

- 全局 `TaskPersistenceProvider` 位于所有路由之外。
- `TaskPersistenceProvider.tsx:106-128` 明确在路由切换后继续轮询运行中的任务。
- 普通 React 局部状态随组件卸载丢失，没有统一的 pause/save/resume 协议。
- 因此当前状态是部分连接被销毁、部分全局任务继续联网，不是统一暂停并保存状态。

另有一处直接冲突：

- `shellTypes.ts:44-50` 把 WordNew/wordflow 的 Pycore bus 设置为关闭。
- `WfDailyReadingSection.tsx:117-129` 又调用 `connectPycoreWs()` 并订阅 `article.published`。
- Shell gate 会阻止该连接，因此 WordNew 无法依赖 Pycore WS 接收实时发布事件，只能依靠 HTTP polling。

## 4. Qwen3TTS foreign process 回收

`managed_service.py:527-598` 把以下条件直接解释为 stale foreign process：

- 服务健康；
- 但 PID 不在当前进程的 managed process map 中。

`tts_service_manager.py:401-464` 随后只根据监听端口查找 PID 并 terminate/kill，没有检查：

- 命令行是否为 Qwen3TTS；
- 可执行文件路径；
- 项目或实例身份；
- owner token；
- 是否为另一合法 Pycore 实例。

这可能误杀手动启动的健康服务、另一 Pycore 实例或占用相同端口的其他程序。

此外，`qwen3tts_service.py:119-137` 支持附着已有健康服务，与 managed service 的强制回收策略冲突。

## 5. TranslationWorker HTTP 超时

`base_laravel_worker.py` 当前配置：

- 单次 HTTP timeout：8 秒；
- result POST：最多 3 次；
- backoff：0.5 秒、1.5 秒。

所以 `retry 2/2` 是既定重试策略，不是根因。

Laravel 的 `TaskManagerService::getTaskStats()` 仍会对持续增长的 `global_tasks` 执行无 WHERE 的全表 `GROUP BY status`。源码注释明确指出，在单 worker PHP runtime 中，该查询会串行阻塞其他请求，包括 health、pull 和 result。

Queue Center snapshot 还可能同步等待 AssistOverview 8 秒。Laravel 单 worker 拥塞、全表统计和远程端点超时可以共同造成 pull/result timeout。

## 6. Queue Center 与 RPC v2

### 6.1 UI 先启动、后端后启动

`useQueueCenterHub.tsx:160-178` 在 `isWsConnected()` 为 false 时直接返回：

- 不发送 snapshot RPC；
- 不增加失败计数；
- 不订阅 WS welcome/connected 状态以立即重试。

后续恢复只能依靠：

- `operation.changed`；或
- Auto Refresh 的 30 秒 fallback interval；或
- 用户手动刷新。

如果 Auto Refresh 被关闭，UI 先打开而 Pycore 后启动时，Queue Center 可能一直保持 Offline/Unreachable。

### 6.2 RPC deadline 与重连

`PycoreWs.ts:273-301` 从 RPC 入队时就建立固定 deadline。断线重连只重发请求，不刷新总预算。

请求在重连完成前可能已经耗尽 30 秒；welcome 后重发时会立即或很快超时。

### 6.3 Current URL / Local 目标语义

Current URL 和 Local 都使用页面 hostname。远程浏览器访问页面时，“Local (this machine)”并不是浏览器本机，而是网页服务器主机，标签与实际行为不一致。

### 6.4 Queue Center 聚合延迟

Queue Center RPC handler 已通过线程执行，没有直接在 Uvicorn event loop 中运行同步聚合。但一次 snapshot 仍串行组合多个切片，并可能等待远程 AssistOverview 8 秒。调用方必须等待整份 snapshot，导致所有面板一起显示 unavailable。

## 6.1 后台任务未经 UI 显式开启

`callmodule_main.py` 中存在多个默认或无条件启用入口：

- `laravel_log_mirror`：`enabled=True`；
- `global_task_worker`：`enabled=True`；
- translation queue monitor：读取默认启动配置；
- translation worker 与 global task worker 同时调用同一个 `poll_once()`。

因此 UI 关闭 translation lane 后，global transport 仍可能注册、heartbeat、pull 并执行其他 lane 任务。

当前 UI 控制的是部分 callback/lane，不是“所有后台 task 的唯一启动授权”。

## 6.2 MCP Chrome 对齐

### Word Validity 错误表名

`AppQyV1LangDictionaryModel::forLanguage()` 会在实例上动态设置正确表名 `app_qy_v1_tts_cache_{lang}`。

`AppQyV1VocabularyValidityController.php:50-78` 的流程是：

1. 创建正确的动态表实例；
2. `hasTable($dictModel->getTable())` 使用该实例，所以检查通过；
3. 随后调用 `$dictModel->query()`；
4. Eloquent `query()` 新建默认模型，丢失动态 `$table`；
5. 查询退回推导表名 `app_qy_v1_lang_dictionary_models`。

这与日志中的 Undefined table 完全一致。

### Task Tab Stop 无效

MCP Chrome 的 Stop 只执行本地动作：

- `taskCenter.stopAll()`；
- 停止 validity runner；
- 清理 Bing runtime；
- 清除本地 run intent/runtime。

它没有调用 Laravel task cancel/release API。

`SimpleWorkerBase.stop()` 还明确允许当前 `cycleInFlight` 和已经开始的 browser task 继续完成。已领取但尚未执行的任务会留给 Laravel timeout reclaim，因此 Laravel UI 仍可能显示 RUNNING。

## 7. Result POST 409

409 的根因是 Laravel lease 与真实执行时间不一致：

- Worker handler 通常只在任务开始时发送一次 `processing`。
- Laravel 只有收到新的 `processing` POST 才延长 `timeout_at`。
- Worker heartbeat 不延长每个 task lease。
- 长任务超过 `timeout_seconds` 后，`releaseTimedOutTasks()` 会释放并重新分配任务。
- 旧执行器不会被取消，仍会继续计算。
- 旧执行器提交最终结果时 owner 已改变，Laravel 返回 409。
- Pycore 对 409 直接丢弃结果。

另外，Pycore `_dispatch()` 使用至少 300 秒的本地 in-flight TTL，即使 Laravel lease 更短。这会扩大 Laravel 已重派、旧 Pycore 仍认为任务执行中的时间窗口。

默认 worker ID 仅按 hostname 生成；同一主机运行多个 Pycore 且未设置 `PYCORE_WORKER_INSTANCE` 时会共享 ID，进一步破坏 worker ownership 和计数。

## 8. Queue Center 设置与 Endpoint

### 8.1 UI 与后台启动状态不一致

RPC 服务通过 `rpc_enabled=True` 在 Pycore 启动配置中直接启用，不受 Queue Center UI 控制。

任务 transport 同样存在无条件启用入口。因此可能同时出现：

- Queue Center UI 显示 RPC Offline；
- 后端 global task worker 已经拉取并执行任务。

### 8.2 Laravel Endpoint 保存与同步

当前实现只有后端持久化：

- `laravel_endpoint_manager.py` 写入 `user_data.json` 的 `laravel_api` section；
- 前端没有保存 selected Laravel endpoint。

`PcLaravelEndpointContext.tsx` 在 Pycore RPC 离线时：

- 使用 prepared endpoints；
- 把 current 设置为 prepared 列表第一项；
- 因而启动阶段会看起来像 endpoint 被重置。

首次失败后只安排一次 3 秒重试；该重试再次失败时不会继续安排，也没有在 WS welcome 后 reload。Pycore 稍晚启动时，前端可能一直保持 fallback endpoint。

当前未实现“前后端各保存一份，连接后以前端为准”的同步策略。

### 8.3 Backend unreachable

`Backend unreachable` 不是单一 health route 问题，而是以下因素叠加：

- Queue Center 不监听 WS welcome 后立即刷新；
- Endpoint context 只重试一次；
- 前端 fallback current 可能与后端 stored current 不一致；
- Laravel AssistOverview 可能等待远程 endpoint 8 秒后超时；
- Queue Center 将整份聚合快照的失败表现为所有面板不可用。

## 9. Agent History RPC 30 秒超时

存在两类放大因素：

1. 所有勾选工具在页面载入时并发调用 `ui.agent_history.test_extract`，没有并发上限。
2. `agent_history_sessions` operation 把最多 8000 条 prompts 放入单个 item 的 `result_json`。

`OperationService.get_snapshot()` 返回完整 operation items 和完整 `result_json`，没有分页或响应大小限制。因此 `ui.operation.snapshot` 可能同时承担：

- SQLite 读取大型 JSON；
- Python 对象构造；
- WebSocket JSON 序列化；
- 一次性传输最多 8000 条提示词。

这些请求虽然通过工作线程执行，但客户端仍使用固定 30 秒 RPC deadline。客户端超时后，后台扫描/读取线程不会随请求取消。

## 10. AssistOverview 诊断字段

`task_center_assist.py` 把 AssistOverview timeout 固定为 8 秒。日志中的 `response_time_ms: 8161` 与该设置一致，表示目标 Laravel 在预算内没有返回 HTTP 响应。

因此：

- `http_status=None` 对 transport timeout 是合理的；
- 当前无法从该日志判断服务器返回了哪种 HTTP 错误，因为根本没有响应。

同时存在两个诊断语义问题：

- `get_queue_overview()` 即使 Assist 请求失败仍固定返回 `success=True`，导致 `_capture_slice()` 记录 `status: success`。
- `_capture_slice()` 读取 `age_ms`，而 overview 返回的是 `age_s` 和 `laravel_snapshot_age_s`，所以 `cache_age_ms` 会显示 None。

当前源码在失败返回中已经包含 `laravel_endpoint`，所以原日志中的 `laravel_url=None` 与当前代码不一致，和第 1 项一样提示运行中的进程可能不是当前源码版本。
