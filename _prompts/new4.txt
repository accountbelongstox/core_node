 总结

 ### 一、为什么 Caddy 申请不到证书（根因已确诊 + 实证）

 caddy-dns/dnspod 模块 bug（当前编译进 frankenphp 的版本 fb7cc31cc04c，master 分支源码与之一致，上游未修复）：

 1. AppendRecords 调 DNSPod Record.Create 后，把 API 响应里的 record 对象直接转成 libdns Record 返回；
 2. 实证：我真实创建了一条 _diag-probe TXT，API 响应为 {"record":{"id":"...","name":"_diag-probe","status":"enabled","weight":null}} —— 不含
    value/type/ttl；
 3. 于是返回给 certmagic 的 Record Data=""，与 ACME keyAuth 永远不相等 → no memory of presenting a DNS record → 签发永久失败，且 CleanUp 也不
    执行 → 泄漏 TXT 记录（10 条已全部清理，剩余 0；我的探测记录也已删除）。
 4. libdns RecordAppender 契约要求“返回所添加的记录”——该模块违反契约，这是 certmagic 其他 provider 也出现同类报错的已知失败模式。

 为什么本机 certbot 成功：certbot 用的是 certbot-dnspod 插件，自己直接调 API、不依赖 libdns 的“返回值回读”环节，所以 token 本身有效（记录确实
 建出来了），坏的是模块的返回值处理。

 ### 二、修复方案：先申请证书，再启动服务

 复用仓库里现成的 acme.sh 预签发设计（frankenphp_acme_sh_install.sh，dns_dp = DNSPod 官方支持，DP_Id/DP_Key 即现有 token 拆分）：

 - 预检流程（laravel_runtime_frankenphp.sh）：每次服务启动 → fm_cert_status（打印证书/模块/token 诊断）→ acme_sh_preflight_for_service（先签发
   /续期证书，SAN 覆盖 apex + *.apex + *.prefix.apex）→ 再渲染 Caddyfile → 再启动。失败仅告警不阻断启动。
 - tls 门控翻转（3 个 shell 渲染器 + PHP builder 字节同步）：磁盘预签证书优先，损坏的 dnspod 模块降级为回退。
 - TimeoutStartSec=900s（systemd 单元生成器新增参数，175 脚本传入），容纳首次签发约 2–5 分钟。
 - 续期：acme.sh 自带 cron + --reloadcmd 通过 caddy admin /load 热加载。

 ### 三、HTTPS 反代 + 0.0.0.0 拓扑

 主 Caddyfile 新增 :9000 HTTP 后端块（php_server，绑定所有接口，即 nginx-plane 契约端口），并按需 import routes/*.caddy（域名的 reverse_proxy
 127.0.0.1:9000 从此真正可用；此前服务端渲染会把 import 行冲掉）。路由文件中 apex/www 重定向块也补了同一张证书的 tls 指令（消除 caddy 内置
