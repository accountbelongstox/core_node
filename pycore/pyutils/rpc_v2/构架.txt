-------------------
RPC v2 desktop UI standard

1. ``pycore-manager`` must use the native RPC v2 WebSocket client for every
   request. UI code must not call FastAPI, fetch, XMLHttpRequest, Axios, or a
   loopback HTTP endpoint for pycore operations.
2. Every request carries a client-generated ``event_id`` and the stable
   ``client_id`` from the WebSocket URL. The server records both before it
   starts the handler.
3. Completion is delivered as a WebSocket response containing ``event_id`` and
   ``client_id``. The client acknowledges the same event only after the result
   has been accepted by the pending callback.
4. The server keeps completed results in the request event table and inventory
   table until the matching client ACK is received. If the client is offline,
   the result remains pending and is replayed after reconnect or on heartbeat.
5. RPC calls have no client-side or RPC-bridge timeout. A disconnected client
   keeps its pending event and reconnects with the same event ID; a completed
   event is replayed instead of being executed again.
6. Long-running work must run in a worker or service task so the WebSocket
   receive loop stays responsive. No route may block the receive loop with a
   synchronous wait for client notification.
7. ``pycore-manager`` has no FastAPI compatibility entry. Its operations are
   registered only as native RPC v2 WebSocket routes. Legacy routers are not a
   supported UI transport and must not be called by the UI.
8. Binary data used by the UI must be transferred through an RPC v2 WS route
   (base64 or a chunked payload). Browser media URLs and external Laravel API
   URLs are not RPC request channels.
9. RPC route names are defined once in the frontend route registry and once in
   the backend route registry. UI components and backend registration modules
   import those registries; literal ``pycore.xxx.xxx`` strings are forbidden
   outside the registries.

-------------------
Route and business-layer boundary

1. ``pycore/callmodule/routers`` and ``pycore/callmodule/rpc_routes`` must not be
   physically merged. ``rpc_routes`` is the only UI route registration layer;
   legacy routers are retained only while non-UI callers are migrated and are
   never an entry point for pycore-manager.
2. Shared validation, orchestration, persistence, and external service calls
   belong in ``controllers`` or ``services``. Neither adapter may duplicate
   business logic.
3. ``rpc_routes`` registers every UI-facing route through the rpc_v2 server and
   delegates work to the shared controllers/services. Each handler receives the
   RPC ``request_id`` and context so event/client ownership is preserved.
4. No new FastAPI-only endpoint may be added. Every migrated UI operation must
   have one named frontend/backend RPC registry entry and one native handler.
5. The RPC adapter must use worker/task dispatch for blocking work. FastAPI
   request objects, HTTP response classes, and HTTP method semantics must not
   leak into shared business code.
